## 1. 회원·인증 정책

| 항목 | 정책 |
| --- | --- |
| 가입·로그인 | GitHub OAuth2로만 가입·로그인한다. 로그인 인가 범위는 `read:user`, `user:email`로 최소화한다. |
| 저장소 권한 분리 | 로그인 인가와 저장소 쓰기 권한은 분리한다. GitHub 커밋 연동은 사용자가 별도로 인가한 경우에만 활성화한다(§9.3). |
| 학습 프로필 | 가입 시 진단을 강제하지 않는다. 맞춤 추천을 요청할 때 목표(취업·학습 등)·선호 언어·활동 시간대 입력을 안내하고, 태그에 처음 진입할 때 진단 응시와 Lv.1 시작 중 하나를 고르게 한다(§8.3). 미입력 사용자도 문제 풀이·스터디 검색·가입 등 일반 기능은 이용할 수 있다. |
| 권한 | 전역 권한은 `USER`, `ADMIN` 두 가지다. 스터디장·운영진은 스터디별 관계 권한(§7), 문제 작성자는 문제별 소유 권한으로 관리한다. 관리자 API는 Gateway와 소유 서비스 양쪽에서 권한을 검증한다. |
| 인증 전달 | Gateway가 JWT를 검증한 뒤 `X-User-Id`, `X-User-Role` 헤더로 전달한다. 외부 요청에 포함된 동일 헤더는 Gateway에서 제거한다. 내부 서비스 포트는 외부에 공개하지 않는다. |
| Refresh Token | Redis에 사용자별로 저장하고 재발급 시 교체(Rotation)한다. 이미 교체된 토큰으로 재발급을 시도하면 해당 사용자의 모든 Refresh Token을 폐기한다(`AUTH_REFRESH_TOKEN_REUSED`). |
| 로그아웃 | Refresh Token을 삭제하고, Access Token은 남은 수명 동안 Redis 차단 목록에 등록한다. |
| 개발용 인증 우회 | `local`, `dev` 프로필에서만 `X-User-Id` 헤더 주입을 허용한다. `prod`·`staging` 프로필에서 활성화 설정이 감지되면 애플리케이션 기동을 실패시킨다. |
| 회원 정지 | `SUSPENDED` 회원은 조회만 허용하고 제출·시험 참가·스터디 가입·힌트 요청·게시글 작성을 `MEMBER_SUSPENDED`(403)로 차단한다. 사유·집행자를 감사 로그에 남긴다. |
| 회원 탈퇴 차단 | 다음 중 하나라도 해당하면 탈퇴를 차단한다. ① 시험·대회에 **실제로 입장한** 참가자는 해당 시험·대회가 `FINALIZED`될 때까지 → `WITHDRAWAL_BLOCKED_ACTIVE_EXAM`(409). 참가 등록만 하고 입장하지 않았으면 탈퇴를 허용한다. ② `CLOSED`가 아닌 스터디의 스터디장 → `WITHDRAWAL_BLOCKED_STUDY_LEADER`(409, 위임 또는 종료 안내) |
| 회원 탈퇴 처리 | 차단 조건이 없으면 탈퇴를 허용하고 `MemberWithdrawn` 이벤트로 연관 데이터를 정리한다. 일반 스터디원 가입은 `LEFT`, 대기 중 가입 신청은 `CANCELED`로 자동 전이한다(§9.4). |

### 2.2 불변식

```
[제출]
submission.problem_revision_id = 접수 시점에 고정한 문제 수정 회차 (이후 변경 불가)
submission.judge_attempt       = 채점 회차, 재채점마다 +1 (감소 불가)
(user_id, idempotency_key)     = 유일

[채점 작업]
(submission_id, judge_attempt)  = judge_jobs 유일
선점 조건: status = PENDING | RETRY_WAITING  AND  next_run_at <= now
결과 저장 조건: job.status = RUNNING  AND  lease_token = :token
try_count <= 3   (초과 시 submissions.FAILED)

[채점 메시지 — EXAM·CONTEST]
SQS Visibility Timeout(120초) > 메시지 수신 + judge_jobs 저장 + 삭제 처리 시간

[시험 — 개인 종료 시각]
FIXED 모드:  personal_ends_at = exam.ends_at   (수동 종료 시 종료 누른 시각)
WINDOW 모드(P3): personal_ends_at = min(participant.started_at + exam.duration, exam.window_ends_at)

[시험 제출 유효성]
exam_submission.received_at <= personal_ends_at   (contest-service 접수 시각 기준)
																									(채점 완료 시각 아님)
(participant_id, problem_id, draft_seq) = 유일

[Draft]
새 Draft 반영 조건: incoming.seq > stored.seq   (같거나 작으면 무시)
Draft 반영 조건: 서버 접수 시각 <= personal_ends_at

[결과 확정]
exam.status = FINALIZED  ⇒  해당 시험 제출 중 COMPLETED / FAILED(0점 확정 기록) 가 아닌 건 = 0

[스터디]
studies.member_count = APPROVED 회원 수 <= studies.capacity        (조건부 UPDATE로 강제)
study_member_quotas.active_count = 회원별 APPROVED 스터디 수 <= 5   (조건부 UPDATE로 강제)
스터디별 APPROVED LEADER = 정확히 1명 (CLOSED 제외)         (leader_key 유일 인덱스로 강제)
가입 트랜잭션 확보 순서 = 회원 카운터 → 스터디 정원

[진행률]
(assignment_id, member_id)             당 과제 상태 1건
(assignment_id, member_id, problem_id) 당 진행 기록 1건
인정 근거 제출은 context = PRACTICE 인 AC 제출, 인정 판정은 problem_id 기준(회차 무관)
completion_type = f(submitted_at, assignment.starts_at, assignment.deadline_at, allow_pre_solved)
진행 기록 반영 조건: incoming.judge_attempt > stored.judge_attempt (같은 제출 기준)
EXCLUDED 문제는 진행률 분모에서 제외

[태그 레벨]
(member_id, tag_id) 당 레벨 1건
level = max(진단 결과들)  → 단계별 승급 기준을 차례로 적용  (진단 미응시면 Lv.1에서 시작)
진단 재응시: level = max(현재 레벨, 진단 결과)   (하향 없음)
승급 집계 대상 = context = PRACTICE 인 제출만
반영 조건: incoming.judge_attempt > stored.judge_attempt (같은 제출 기준)
레벨·성취도는 저장값 증감이 아니라 현재 데이터로 재계산

[진단]
(member_id, tag_id) 당 진행 중 진단 = 최대 1건
응시 가능 조건: tag_level IN (Lv.0, Lv.1, Lv.2)  AND  now >= 직전 진단 종료 시각 + 3일
종료 시각 = min(최종 제출 시각, started_at + 60분)
종료 이후 접수된 저장·제출은 반영하지 않는다

[힌트 차단]
(member_id, exam_ref, problem_id) = 유일
차단 조건: starts_at <= now < ends_at  AND  now < ends_at + 10분
진단 진행 중에는 모든 문제의 힌트를 차단한다
확인 시점: 요청 접수 시 + READY 전이 직전
```

### 2.3 사용자 이탈 구간별 복구

| 구간 | 복구 기준 | 복구 방법 | 재진입 조건 |
| --- | --- | --- | --- |
| 제출 직후 결과 대기 중 | 제출은 서버에 접수되어 있음 | 재접속 시 제출 이력에서 상태 조회, SSE 재연결 시 `Last-Event-ID`로 채점 완료 알림 재전송 | 없음 |
| 제출 요청 응답 유실 | `Idempotency-Key` 보관 기간(24시간) 내 | 같은 키로 재요청하면 기존 `submissionId` 반환 | 키를 바꾸면 새 제출로 처리 |
| 시험 제출 응답 유실 | 같은 `(참가자, 문제, seq)` | 같은 `seq`로 재요청하면 기존 `examSubmissionId` 반환 | 코드를 바꾸면 새 `seq`로 제출 |
| 시험 진행 중 이탈 | `personal_ends_at` 이전 | 시험 화면 재진입 후 서버 Draft와 LocalStorage 중 `seq`가 큰 쪽으로 복구 | 종료 후에는 결과 화면으로 이동 |
| 시험 종료 시점에 오프라인 | 서버에 저장된 최신 Draft 기준 | 종료 시 서버 Draft로 자동 제출 | LocalStorage에만 있던 변경분은 반영되지 않음(시험 화면에 안내) |
| 진단 진행 중 이탈 | 시작 + 60분 이전 | 재진입 시 남은 시간으로 이어서 응시하고, 서버 Draft와 LocalStorage 중 `seq`가 큰 쪽으로 복구 | 종료 후에는 결과 화면으로 이동 |
| 진단 종료 시점에 오프라인 | 서버에 저장된 최신 Draft 기준 | 만료 스케줄러가 마지막 제출 이후 변경된 Draft를 자동 제출 | 응시 1회로 기록되고 쿨타임이 시작됨 |
| 힌트 생성 중 이탈 | 힌트 요청이 `GENERATING` 또는 `READY` | 재접속 시 힌트 이력에서 조회, 완료 알림 재전송 | 없음 |
| 스터디 가입 신청 후 미승인 | 신청 후 7일 이내 | 신청 상태 조회, 취소 가능 | 만료 후 재신청 |
| GitHub Sync 실패 | 재시도 횟수 이내 | 자동 재시도 | 최종 실패 시 연동 설정 화면에서 수동 재동기화 |

## 3. 제출·채점 정책

### 3.1 제출

| 항목 | 정책 |
| --- | --- |
| 허용 언어 | Java 17, Python 3, C++17. 목록 밖 언어는 `UNSUPPORTED_LANGUAGE`(400) |
| 난이도 범위 | 문제 난이도는 1~3만 사용한다. |
| 풀이 형태 | 사용자는 `solution` 함수를 구현해 값을 반환한다. Java는 Solution의 public 인스턴스 메서드, Python은 최상위 동기 함수, C++은 전역 solution 함수. C++의 main과 입출력 처리는 실행 코드가 제공한다. |
| 코드 크기 | 64KB 이하. 초과 시 `CODE_TOO_LARGE`(413) |
| 제출 문맥 | 제출은 `context`(`PRACTICE` / `EXAM` / `CONTEST` / `DIAGNOSIS`)와 문맥 ID를 가진다. |
| 진입점 | `PRACTICE`: 클라이언트 → `judge-service` `POST /submissions`, <br>`EXAM`·`CONTEST`: 클라이언트 → `contest-service`가 접수·검증 후 `ExamSubmissionRequested`/`ContestSubmissionRequested` 이벤트로 `judge-service`에 채점 요청. `judge-service`는 이 이벤트로만 `EXAM`·`CONTEST` 제출을 생성한다., <br> `DIAGNOSIS`: 진단 세션을 소유한 `member-service`가 접수·검증 후 채점을 요청한다(세부 경로 확정 필요). |
| 제출 대상 | `PRACTICE`는 `scope = GENERAL`·`visibility = PUBLIC` 문제 중 해당 태그의 사용자 레벨이 허용하는 난이도까지만(§8.3). `EXAM`·`CONTEST`는 시험·대회에 고정된 문제 회차만. `DIAGNOSIS`는 진단이 출제한 문제만(레벨 제한 미적용). `PRIVATE`·`ARCHIVED` 문제의 `PRACTICE` 제출은 `PROBLEM_NOT_AVAILABLE`(404) |
| 멱등 처리 | **일반 풀이(`PRACTICE`)**는 `Idempotency-Key` 헤더가 필수다. 접수 후 24시간 동안 같은 사용자·같은 키·같은 본문 요청에는 기존 제출을 반환한다. 유효 기간 안에 같은 키로 다른 본문을 보내면 `IDEMPOTENCY_KEY_CONFLICT`(422)로 처리한다. 유효 기간이 지나 같은 키로 들어온 요청은 사전 검증을 다시 수행하여 새 제출로 접수한다. **시험·대회 제출**은 각각 `examSubmissionId`·`contestSubmissionId`를 멱등키로 사용한다. 같은 접수 ID의 요청이 다시 전달되면 기존 제출로 처리하며, 일반 풀이의 24시간 만료 규칙을 적용하지 않는다. |
| Rate Limit | 사용자당 분당 10회, 동일 문제 5초 간격. 시험·대회 제출은 `contest-service`에서 같은 기준을 적용한다(자동 제출은 제외). 초과 시 `SUBMISSION_RATE_LIMITED`(429)와 `Retry-After` |
| 접수 응답 | 검증 통과 시 제출(`QUEUED`)·채점 작업(`judge_jobs`, `PENDING`)·테스트별 결과 자리를 한 트랜잭션에 저장하고 `202 Accepted`와 접수 ID를 반환한다. 채점 결과는 접수 응답에 포함하지 않는다. |
| 코드 실행(Run) | 제출과 분리된 실행 경로다. 공개 테스트케이스와 사용자 직접 입력 테스트만 실행하고, 제출 이력·결과 저장·이벤트 발행이 없다. 채점 파이프라인을 거치지 않고 Judge0를 동기 호출한다. |
| 제출 이력 | 모든 문맥의 제출을 본인 제출 이력에 표시하고 문맥을 함께 보여준다. 시험·대회 제출은 일반 통계·태그 레벨·스터디 진도·GitHub 동기화에 반영하지 않는다. 진단 제출은 이력에 표시하되 승급 집계(해결 문제 수·성취도)에 포함하지 않는다. |
| 코드 열람 | 제출 코드는 본인과 관리자만 열람한다. 작성자가 공유한 AC 코드만 공유 범위 안의 사용자에게 공개한다(§4.1). |

**문맥별 제출·공개 정책**

| 문맥 | 재제출 | 판정 공개 시점 | 점수 기준 | 재제출 비용 | AC 이후 제출 |
| --- | --- | --- | --- | --- | --- |
| `PRACTICE` | 허용(Rate Limit) | 채점 완료 즉시 | 없음 | 없음 | 이력 기록 |
| `EXAM` | 종료 전 허용(Rate Limit) | `IN_PROGRESS`: 공개 테스트 결과만 / `CLOSED`: 잠정 점수·순위 / `FINALIZED`: 확정 결과 | 문제별 마지막 유효 제출의 부분 점수 | 없음(마지막 제출이 점수) | 마지막 제출로 점수 갱신 |
| `CONTEST` | 종료 전 허용(Rate Limit) | 채점 완료 즉시 | ICPC: 맞힌 문제 수 → 패널티 시간 | AC 전 오답 1회당 20분(`CE`·`SYSTEM_ERROR` 제외) | 순위 영향 없음 |
| `DIAGNOSIS` | 제한 시간 안에서 허용 | 진단 종료 후 | 문항별 최종 제출을 결과로 반영. 레벨 판정은 제한 시간 안에 한 번이라도 AC를 받은 문항을 정답으로 본다 | 없음 | 결과·레벨 판정에 반영 |
- 제출 횟수는 네 문맥 모두 제한하지 않는다. "즉시 공개"는 판정을 언제 보여주는가에 대한 정책이며, 대회가 즉시 공개할 수 있는 것은 ICPC 방식이 오답 패널티로 재제출 비용을 매기기 때문이다.
- 숨김 테스트케이스의 입력·출력은 모든 문맥에서 공개하지 않는다.
- 모의 코테는 제출 버튼 옆에 "이전 제출보다 점수가 낮아질 수 있음"을 안내한다.

### 3.2 채점 실행

| 항목 | 정책 |
| --- | --- |
| 실행 방식 | 제출이 고정한 문제 수정 회차의 테스트케이스를 독립적으로 Judge0에 실행 요청한다. |
| 실행 데이터 | 고정 `problemRevisionId`의 함수 명세·실행 제한·전체 테스트 파일 참조를 조회하고, Judge가 비공개 S3에서 입력·기대값을 읽는다. 최초 실행과 재시도는 같은 조회 모듈을 사용하며 제출 가능 여부를 다시 검사하지 않는다. |
| Judge0 호출 | 테스트별로 실행을 생성해 token을 받고 결과를 폴링한다. 호출량이 부담이 되면 배치 제출을 검토한다. |
| 중단 기준 | 네 문맥 모두 전체 테스트를 실행한다. `EXAM`은 부분 점수를 위해 통과 수를 기록한다. 실패·전체 채점 기한 초과 시에는 회차를 실패로 종결할 수 있다. |
| 제한 값 | 기준 제한(`time_limit_ms` 기본 2,000ms, `memory_limit_kb` 기본 262,144KB)을 언어 공통으로 적용한다. `wall_time_limit = cpu_time_limit + 5초`(고정값, 환경변수로 조정 가능). 언어별 보정은 유의미한 차이가 확인되면 도입을 검토한다. |
| 시간·메모리 기록 | 테스트별 실행 시간·메모리 중 최댓값을 제출의 대표값으로 기록한다. |
| 출력 비교 | 함수 반환값을 Judge에서 명세 타입 검사 후 기대값과 비교한다. 문자열의 공백·대소문자·개행을 그대로 비교하며, 배열은 길이·순서·값, 객체는 키 집합·값을 비교한다. 디버그 출력은 반환값과 분리한다. 문제별 비교 방식 선택과 스페셜 저지는 1차 범위에서 제외한다. |
| 결과 공개 범위 | 공개 테스트는 입력·기대 출력·실제 출력을 보여준다. 숨김 테스트는 통과 여부와 번호만 보여주고, 입력·출력은 어떤 API로도 반환하지 않는다. 문맥별 판정 공개 시점은 §3.1 표를 따른다. |
| Run 제한 | `run:{memberId}` 키로 원자성을 보장하는 Rate Limit을 적용한다. 쿨다운(TTL)은 두지 않는다. |
| 이벤트 페이로드 | `SubmissionJudged`(`PRACTICE` 전용)는 공통 헤더(`eventId`·`eventType`·`schemaVersion`·`occurredAt`·`aggregateId`·`correlationId`)와 `submissionId`·`userId`·`problemId`·`problemRevisionId`·`submittedAt`(서버 접수 시각)·판정·`judgeAttempt`·통과 수/전체 수·시간·메모리·문제 난이도·태그 스냅샷을 담는다. 모든 ID 필드는 문자열이고 코드 본문은 담지 않는다. `EXAM`·`CONTEST`는 `ExamSubmissionJudged`·`ContestSubmissionJudged`로 분리 발행하며, `submittedAt`은 `contest-service`의 `received_at`을 그대로 쓴다. |
| 기록 | 케이스별 판정·CPU 시간·메모리, 회차의 통과/전체 수·최대 CPU 시간·최대 메모리. |

### 3.3 판정 매핑

| 판정 | 의미 | Judge0 결과 기준 |
| --- | --- | --- |
| `AC` | 정답 | 모든 테스트가 실행 오류 없이 완료되고, Judge가 함수 명세에 따라 비교한 반환값이 모두 기대값과 일치 |
| `WA` | 오답 | 정상 실행된 테스트의 반환값이 Judge의 타입·값 비교에서 기대값과 일치하지 않음 |
| `TLE` | 시간 초과 | Time Limit Exceeded |
| `MLE` | 메모리 초과 | 측정 메모리 ≥ 메모리 제한 (RE 계열로 종료되더라도 메모리 기준을 우선 적용) |
| `RE` | 런타임 에러 | Runtime Error 계열(SIGSEGV, SIGFPE, SIGABRT, NZEC 등), 출력 크기 초과 |
| `CE` | 컴파일 에러 | Compilation Error. 컴파일 메시지는 본인에게만 표시 |
| (내부) `SYSTEM_ERROR` | 채점 시스템 오류 | Internal Error, Exec Format Error, Judge0 통신 실패·타임아웃 |

| 판정 코드 | 화면 표시 문구 |
| --- | --- |
| `AC` | 정답 |
| `WA` | 오답 |
| `TLE` | 시간 초과 |
| `MLE` | 메모리 초과 |
| `RE` | 실행 중 오류 |
| `CE` | 컴파일 오류 |
- `SYSTEM_ERROR`는 사용자 판정이 아니다. 사용자에게는 "채점 중"으로 보이며 재시도 대상이다(§3.4).
- Judge0는 메모리 초과를 별도 상태로 구분하지 않고 런타임 에러로 반환하는 경우가 있으므로, MLE 판정은 측정 메모리 기준으로 보정한다. 언어별 동작은 1주차 PoC에서 확인한다.

### 3.4 장애·재시도·재채점

| 용어 | 의미 | 증가 시점 |
| --- | --- | --- |
| 채점 회차 `judge_attempt` | 같은 제출을 몇 번째로 채점하는가 | 관리자 재채점·재처리 |
| 실행 시도 `try_count` | 한 회차 안에서 Judge0 실행을 몇 번 시도했는가 | `SYSTEM_ERROR`·임대 만료 |

| 항목 | 정책 |
| --- | --- |
| 작업 원천 | 채점 작업은 `judge-service` 스키마의 `judge_jobs` 테이블을 원천으로 한다. SQS 메시지는 작업 생성 수단일 뿐 원천이 아니다. |
| 작업 생성 | `PRACTICE`·`DIAGNOSIS`는 접수 트랜잭션에서 `submissions`(`QUEUED`)와 `judge_jobs`(`PENDING`)를 함께 저장한다. `EXAM`·`CONTEST`는 `exam-submission-queue` 소비 트랜잭션에서 `processed_events`·`submissions`·`judge_jobs`를 저장한 뒤 메시지를 삭제한다. |
| 작업 선점 | 실행기가 `SELECT … FOR UPDATE SKIP LOCKED`로 동시 처리 수만큼 선점하고 `RUNNING`·`lease_token`·`lease_until = now + 120초`로 전이한다. |
| 임대 연장 | 실행 중 30초마다 `lease_token` 일치 조건으로 임대를 연장한다. |
| 재시도 대상 | `SYSTEM_ERROR`만 재시도한다. `AC`~`CE`는 확정 판정이므로 재시도하지 않는다. |
| 재시도 방식 | `try_count`를 1 올리고 `RETRY_WAITING`으로 전이한 뒤 10초 → 30초 백오프로 다시 선점한다. `try_count`가 3을 넘으면 작업을 `FAILED`로 종결하고 제출을 `FAILED`로 전이한 뒤 "채점 실패, 재처리 예정" 알림을 보낸다. |
| 임대 만료 회수 | 30초 주기 스케줄러가 `lease_until`이 지난 `RUNNING` 작업을 `RETRY_WAITING`으로 되돌린다. 회수도 `try_count`에 포함한다. |
| 장시간 작업 | `RUNNING` 상태로 10분이 지난 작업은 회수 대상이다. |
| 늦은 결과 | 결과 저장은 `job.status = RUNNING AND lease_token = :token` 조건부 UPDATE로 한다. 회수·재채점으로 임대나 회차가 바뀐 뒤 도착한 이전 실행기의 결과는 버린다. |
| 실행 이력 | 실행 시도마다 `judge_job_runs`에 1행을 불변 이력으로 남긴다. |
| 서킷브레이커 | Judge0 장애로 서킷이 열리면 새 작업 선점을 멈춘다. 장애 중 반복 실패로 `try_count`가 소진되어 대량 `FAILED`가 생기는 것을 막는다. |
| 중복 수신 | 시험·대회 채점 요청 메시지가 중복 수신되면 `processed_events` 유일 제약으로 반영 없이 메시지만 삭제한다. |
| DLQ | `exam-submission-queue` 수신 횟수가 3회를 넘은 메시지는 DLQ로 격리하고 운영 알림을 보낸다. |
| 대사(Reconciliation) | 5분마다 제출 상태와 작업 상태가 어긋난 건(§10 대응표)을 찾아 재개하거나 기록한다. |
| 수동 재처리 | 관리자는 DLQ 메시지·`FAILED` 제출을 재처리할 수 있다. 사유·집행자를 감사 로그에 남긴다. |
| 재채점 | 관리자 재채점은 `judge_attempt`를 1 올리고 `(submission_id, judge_attempt)` 유일 제약으로 새 `judge_jobs` 행을 만든다. 이전 회차 결과는 삭제하지 않고 이력으로 보존한다. 대상은 채점 서버 장애로 실패한 `EXAM` 제출이며, 진단 제출 적용 여부는 협의 중이다. |
| 재채점 전파 | 재채점 결과는 문맥별 채점 결과 이벤트(새 `judgeAttempt`)로 다시 발행한다. 소비자는 저장된 회차보다 큰 경우에만 반영한다. |
| 확정된 결과 | `FINALIZED` 시험·대회는 새 재채점·실패 재처리를 허용하지 않는다. 실패한 `EXAM` 제출 재처리는 확정 전에만 허용한다. 확정 후 관리자의 재확정은 기존 유효 채점 기록을 재집계해 새 결과 버전·불변 스냅샷을 저장하는 작업이며, 기존 스냅샷을 보존하고 감사 로그를 남긴다. |
| Judge0 장애 | 제출 접수는 계속 받고 작업을 적체시킨다. 문제·스터디·순위 조회와 시험 진행(Draft 저장·제출 접수)은 영향받지 않아야 한다. 적체 임계값 초과 시 운영 알림을 보낸다. |

## 4. 문제·테스트케이스 정책

문제는 `problem`(용도·공개 상태)과 `problem_revision`(제목·난이도·본문·함수 명세·실행 제한·테스트 구성)으로 나눈다. 식별·고정에는 `problem_revision.id`(`problemRevisionId`)를, 화면 표시에는 `revision_number`를 쓴다.

| 항목 | 정책 |
| --- | --- |
| 작성 권한 | 1차 범위에서는 `ADMIN`만 문제를 작성한다. 일반 사용자 출제는 P3 후보다. |
| 용도 구분 | `problem.scope`는 `GENERAL`(일반용)·`EXAM_ONLY`(시험·대회 전용) 두 가지다. |
| 공개 상태 | `problem.visibility`는 `PUBLIC`(공개)·`PRIVATE`(비공개)·`ARCHIVED`(미사용, 소프트 딜리트) 세 가지다. 일반 공개 문제 조회는 `scope = GENERAL AND visibility = PUBLIC` 조건으로 한다. |
| 난이도 | 1~3만 사용한다. 난이도 4·5는 출제·진단·연습 대상에서 제외한다. |
| 태그 | 프로그래머스 알고리즘 고득점 Kit 기준으로 선정한다. 태그는 레벨·진단·문제집 구성의 공통 기준이다. |
| 작성 단계 검증 | 등록 전에 제목·본문·입출력 형식·제약 조건·제한 값·난이도·태그·공개 테스트 1개 이상·숨김 테스트 1개 이상·정답 코드 AC를 검증한다. 기준 시간 제한은 C++ 정답 코드의 테스트별 최대 실행 시간의 3배 이상, 최소 1,000ms로 한다. |
| 검수 | `IN_REVIEW` 회차는 작성자가 아닌 관리자가 승인·반려한다. 반려 시 사유를 기록한다. 심사 중 회차의 본문·테스트케이스는 수정할 수 없다. (후순위/보류) |
| 검수 도입 전(P0~P1) | 검수 워크플로(P2) 도입 전에는 관리자가 작성 단계 검증을 통과한 회차를 직접 공개한다. 공개 기록은 `problem-service` 자기 DB의 감사 로그로 남긴다. |
| 수정 회차 | 공개된 회차는 수정할 수 없다. 수정하면 새 `problem_revision`이 생성되고, 공개되면 이후 제출부터 새 회차가 적용된다. 이전 회차는 이력으로 보존한다. |
| 저장 방식 | 문제 본문·이미지·테스트케이스는 크기와 무관하게 모두 S3에 저장하고, DB에는 메타 정보(객체 키·버전·체크섬)만 연결한다. 회차별 불변 경로로 보관하며 채점 실행기만 테스트 읽기 권한을 가진다. |
| 이미지 정리 | 이미지는 S3에 저장한 뒤 문제 본문에 연결한다. 본문에 연결되지 않은 이미지는 일정 대기 시간이 지나면 정리한다(대기 시간 확정 필요). |
| 사용 범위 | 스터디 문제집과 모의 코테에는 `scope = GENERAL`·`visibility = PUBLIC` 문제만 추가할 수 있다. 대회에는 `scope = EXAM_ONLY` 문제를 쓸 수 있다. |
| 비공개 처리 | `PUBLIC ↔ PRIVATE` 전환은 관리자만 가능하다. 진행 중 시험·대회에 포함된 문제는 `PRIVATE` 전환을 `PROBLEM_IN_ACTIVE_EXAM`(409)로 막는다. 예정된 시험·대회의 전환 허용 여부는 확정 필요. |
| 상태 변경 전파 | 공개 상태·용도 변경은 `ProblemStateChanged` 이벤트로 발행해 스터디 문제집(`ACTIVE ↔ EXCLUDED`)과 시험에 반영한다(§9.1). |
| 대회 전용 문제 | 대회 종료 전까지 문제 목록·검색·문제집 선택에 노출하지 않는다. 종료 후 공개 여부는 대회 설정을 따른다. |
| 저작권 | 타 사이트 문제를 복제하지 않는다. 고득점 Kit의 태그·난이도 구조만 참고해 팀이 자체 출제하며, 출처가 있는 문제는 라이선스와 출처를 표시한다. |
| 삭제 | 제출이 1건이라도 있는 문제는 삭제하지 않고 `ARCHIVED`로만 전환한다. |

## 5. 모의 코딩테스트 정책

### 5.1 시험 생성·참가

| 항목 | 정책 |
| --- | --- |
| 범위 | 모의 코딩테스트(시험)는 스터디 내부 활동이다. 전체 사용자 대상은 대회(§6)로 구분한다. |
| 생성 권한 | 해당 스터디의 `LEADER`·`MANAGER`. `CLOSED` 스터디에서는 생성할 수 없다. |
| 문제 구성 | `scope = GENERAL`·`visibility = PUBLIC` 문제만 사용한다. 기본 3문제·90분, 개설자가 조정한다. 공개 문제이므로 "처음 보는 문제" 조건은 보장하지 않으며 연습용 평가로 안내한다. |
| 참가 방식 | 1차는 `FIXED`(모두 같은 시각에 시작·종료). `WINDOW`(기간 안에서 각자 시작)는 P3 |
| 참가 자격 | 참가 등록 시점에 해당 스터디의 `APPROVED` 구성원이어야 한다. `contest-service`는 `StudyMemberJoined`/`StudyMemberLeft` 이벤트 복제본으로 판단한다. 복제본에 없으면 `EXAM_NOT_ELIGIBLE`(403) |
| 시험 중 탈퇴 | 시험 시작 후 스터디를 탈퇴해도 이미 등록한 참가는 유지하고 결과에 포함한다. |
| 참가 등록 | 종료 전까지 등록·입장할 수 있으나 종료 시각은 늘어나지 않는다. 종료 시까지 입장하지 않은 참가자는 `ABSENT` |
| 참가 취소 | 시작 전에는 참가를 취소하고 다시 신청할 수 있다. 시작 후에는 문제를 이미 봤을 수 있으므로 취소할 수 없고, 종료 시 한 문제도 제출하지 않은 경우에만 순위표에서 제외한다. |
| 문제 비공개 | 시작 전에는 문제 목록·본문을 참가자에게도 반환하지 않는다(`EXAM_NOT_STARTED`, 403). |
| 문제 회차 고정 | 시험 생성 시 포함 문제의 현재 공개 회차(`problemRevisionId`)를 `exam_problems`에 고정한다. 시험 중 새 회차가 공개되어도 고정 회차로 채점한다. |
| 배점 | 문제별 배점을 생성 시 정한다. 합계 기본 100점 |
| 수정·취소 | 시작 전(`SCHEDULED`)에만 문제·시간·배점을 수정하거나 `CANCELED`할 수 있다. 수정·취소는 `ExamUpdated`·`ExamCanceled` 이벤트로 발행하고 등록자에게 알린다. |

### 5.2 시간 판정

| 항목 | 정책 |
| --- | --- |
| 시간 기준 | 모든 시작·종료·저장·제출 유효성 판정은 서버 시각으로 한다. 클라이언트 타이머는 표시용이다. |
| 잔여 시간 표시 | 서버가 `personal_ends_at`과 서버 현재 시각을 함께 내려주고, 클라이언트는 차이를 보정해 표시한다. |
| 상태 전이 | 스케줄러가 5초마다 시각 도달 시험을 전이하지만, 요청 처리 시에는 상태가 아니라 **서버 시각과 `personal_ends_at` 비교**로 판정한다(스케줄러 지연이 판정에 영향 없음). |
| 마감 후 제출 | 접수 시각 > `personal_ends_at` 이면 `EXAM_CLOSED`(409)로 거절한다. 유예 시간은 두지 않는다(자동 제출이 서버 최신 Draft를 보장). |

### 5.3 Draft 저장

| 항목 | 정책 |
| --- | --- |
| 저장 단위 | 참가자·문제·언어별 Draft 1건 |
| 저장 주기 | 변경된 코드만 저장한다. 입력이 2초간 멈추면 저장하고, 계속 입력 중이어도 최대 10초마다 저장한다. 문제 이동·직접 제출 전에는 최신 코드를 저장한다. |
| 순번 | 클라이언트가 문제별로 1씩 증가하는 `seq`를 붙여 보낸다. 서버는 `WHERE seq < :incomingSeq` 조건부 UPDATE로만 반영한다. |
| 저장 역전 | 늦게 도착한 이전 Draft(`seq`가 같거나 작음)는 무시하고 200으로 응답하되 `applied=false`와 서버 `seq`를 반환한다. |
| 저장 상태 표시 | 화면에 저장 성공 여부와 마지막 서버 저장 시각을 표시한다. 연결 실패 시 "미저장" 상태를 표시하고 재접속 후 시험 시간 안에서 다시 저장한다. |
| 이중 보관 | 클라이언트는 모든 변경을 LocalStorage에도 `seq`와 함께 저장한다. 재진입 시 서버 Draft와 비교해 `seq`가 큰 쪽을 보여주고, LocalStorage가 크면 즉시 서버에 저장한다. |
| 저장 빈도 제한 | 참가자당 초당 1회. 초과 요청은 마지막 요청만 반영한다. |
| 종료 후 | 접수 시각이 `personal_ends_at`을 넘은 저장은 `EXAM_CLOSED`(409) |
| 적용 범위 | 진단 테스트(§8.3)도 같은 Draft 규칙을 적용한다. |

### 5.4 시험 제출·종료·점수

| 항목 | 정책 |
| --- | --- |
| 직접 제출 | 참가자가 제출하면 `contest-service`가 ① 시간·자격 검증 ② 해당 코드·`seq`로 Draft 반영 ③ `exam_submissions`(접수 시각·`draft_seq`)와 Outbox를 한 트랜잭션에 저장하고 `202` + `examSubmissionId`를 반환한다. |
| 채점 연결 | `judge-service`는 `ExamSubmissionRequested`(페이로드에 `receivedAt` 포함; DB `received_at`을 직렬화)를 소비해 `context = EXAM` 제출을 만든다(멱등키 = `examSubmissionId`). 채점 결과는 `ExamSubmissionJudged`로 돌아와 `exam_submissions`에 연결된다. |
| 회원 정지 | SUSPENDED는 신규 참가 등록·입장·Draft 저장·직접 제출·Run을 차단한다. 정지 전 유효 접수의 채점·점수·순위와 서버에 저장된 Draft의 자동 제출은 유지한다. 기존 기록 읽기·동일 접수 재요청 반환은 허용하며 정지 해제 시 별도 재집계를 하지 않는다. 대회에도 같은 규칙을 적용한다. |
| 자동 제출 대상 | 개인 종료 시각에 문제별로 "마지막 시험 제출 이후 저장된 Draft(`draft.seq > 마지막 제출 seq`)"가 있으면 그 Draft를 제출한다. 한 번도 제출하지 않았고 Draft가 비어 있지 않은 문제도 대상이다. |
| 자동 제출 실행 | 종료 시각 + 3초 처리 유예 후 실행한다. `received_at`은 `personal_ends_at`으로 기록한다. 유예 중 도착한 저장·제출 요청은 접수 시각 기준으로 판정되므로 종료 이후 요청은 거절된다. |
| 중복 방지 | `(participant_id, problem_id, draft_seq)` 유일 제약으로 1회만 생성한다. 직접 제출과 같은 `seq`면 자동 제출은 유일 제약 위반을 "이미 제출됨"으로 처리하고 넘어간다. 종료 작업을 재실행해도 결과는 같다. |
| 수동 종료 | 참가자가 "시험 종료"를 누르면 그 시각을 개인 종료 시각으로 확정하고 자동 제출을 실행한다. 이후 재입장해도 저장·제출할 수 없다. |
| 문제 점수 | 문제별 **마지막 유효 제출** 기준 `배점 × 통과 테스트 수 / 전체 테스트 수` (소수점 둘째 자리 버림). 제출 화면에 "이전 제출보다 점수가 낮아질 수 있음"을 안내한다. |
| 컴파일 에러 | 0점. 오답 횟수 패널티는 없다. |
| 시험 점수 분리 | 시험 제출은 일반 풀이 통계·태그 레벨 갱신·스터디 진행률·GitHub 동기화에 반영하지 않는다(시험 문제가 공개 문제여도 동일). 시험 전 정답 기록도 시험 점수에 반영하지 않는다. |
| 잠정 결과 | 시험이 `CLOSED`가 되면 채점 진행률(종결 수/전체 수)과 함께 잠정 점수·순위를 시험 화면에 공개하고, 채점이 끝날 때마다 SSE로 갱신한다. 잠정 결과는 알림으로 보내지 않는다. |
| 결과 확정 | 해당 시험 제출이 모두 `COMPLETED`·`FAILED`가 되면 DB 기준으로 점수·순위를 재계산해 `FINALIZED`로 전이하고 확정 결과를 공개한 뒤 알림을 보낸다. |
| `FAILED` 제출 | 확정 시점에 `FAILED` 제출이 있으면 확정을 보류하고 관리자에게 알린다. 관리자가 재처리하거나 0점 확정을 사유와 함께 기록한 뒤 확정한다. |
| 시험 순위 | 총점 내림차순 → 마지막 유효 제출 시각 오름차순. 모두 같으면 공동 순위 |
| 분석 리포트(P3) | 문제별 정답률·제출 횟수, 개인별 제출 시점·판정 변화·최초 제출~최초 정답 경과시간(실제 풀이 시간으로 해석하지 않으며 기록이 없으면 "미산정"), 미해결·오답 문제를 다음 문제집 후보로 제공 |

| 제출 | 시험과 같이 `contest-service`가 접수·시간 검증 후 `ContestSubmissionRequested` 이벤트로 채점을 요청한다. |
| 순위 기준 | ① 맞힌 문제 수 내림차순 ② 패널티 시간 오름차순 ③ 마지막 AC 시각 오름차순 |
| 패널티 시간 | 맞힌 문제마다 `(대회 시작부터 AC 접수까지 분) + (그 문제 AC 전 오답 수 × 20분)`의 합. 맞히지 못한 문제의 오답은 패널티가 없다. |
| 패널티 제외 | `CE`, `SYSTEM_ERROR`는 오답 횟수에 포함하지 않는다. |
| AC 이후 제출 | 이미 맞힌 문제의 추가 제출은 순위에 영향을 주지 않는다. |
| 동점 | 세 기준이 모두 같으면 같은 순위를 부여한다. |
| 실시간 순위 | Redis Sorted Set의 score는 0으로 고정하고, 해결 수 내림차순·패널티 분 오름차순·마지막 최초 AC 접수 시각 오름차순·memberId 오름차순을 고정 폭 lex 키로 표현한다(DB §6.4.2, 스케줄러 §4.8). memberId는 표시 순서만 안정화하고 공동 순위 판정에서 제외한다. 부동소수 합성 점수로 시각 정밀도를 줄이지 않는다. |
| 순위 원천 | Redis는 조회용이다. 원천 데이터는 `contest-service` DB의 참가자별 문제 결과이며, 결과 확정 시 DB 기준으로 재계산해 Redis를 재구성한다. Redis 장애 시 DB에서 재구성한다. |
| 반영 방식 | `ContestSubmissionJudged`를 받아 참가자·문제 결과를 갱신하고(회차 비교) Redis 점수를 원자적으로 갱신한 뒤 SSE로 순위 변경을 알린다. |
| 참가 취소 | 시작 전에는 취소·재신청을 허용하고, 시작 후에는 취소할 수 없다. 한 문제도 제출하지 않은 참가자는 순위표에서 제외한다. |
| 순위 동결 | 종료 전 순위 동결(Freeze)은 1차 범위에서 제외한다(P3 후보). |
| 결과 공개 후 | 종료된 대회 문제의 공개 여부는 대회 설정을 따른다. 종료 후 제출은 대회 결과에 반영하지 않는다. |

## 7. 스터디 정책

| 항목 | 정책 |
| --- | --- |
| 생성 | 로그인 사용자는 스터디를 만들고 `LEADER`가 된다. 추천·검색 화면에서 넘어오면 해당 조건(목표·난이도·언어·활동 시간)을 초기값으로 제공한다. |
| 정원 | 스터디당 2~10명(스터디장 포함), 기본 10명. 현재 인원보다 작게 변경할 수 없다. |
| 참여 상한 | 1인 동시 참여(`APPROVED`) 스터디 최대 5개. 회원별 카운터 `study_member_quotas.active_count`를 조건부 UPDATE(`WHERE active_count < 5`)로 확보한다. 영향 행이 0이면 `STUDY_JOIN_LIMIT_EXCEEDED`(409). 가입 트랜잭션은 ① 회원 카운터 → ② 스터디 정원 순서로 확보하고, 둘 중 하나라도 실패하면 전체를 롤백한다. 카운터 행은 첫 가입 시 생성한다. |
| 가입 방식 | `INSTANT`(즉시 가입) / `APPROVAL`(승인 가입). 추천되지 않은 스터디도 누구나 상세 조회·가입 신청할 수 있다. |
| 정원 검증 | 즉시 가입과 승인 처리 모두 `studies.member_count`를 조건부 UPDATE(`SET member_count = member_count + 1 WHERE id = ? AND member_count < capacity`)로 먼저 확보한 뒤, 같은 트랜잭션에서 가입을 `APPROVED`로 만든다. 영향 행이 0이면 `STUDY_FULL`(409)로 거절한다. 탈퇴(`LEFT`)·강제 탈퇴(`REMOVED`)는 같은 트랜잭션에서 `member_count`를 1 줄인다. |
| 중복 신청 | 같은 스터디에 `PENDING`·`APPROVED` 상태가 있으면 `STUDY_ALREADY_APPLIED`(409) |
| 신청 취소·만료 | 승인 전까지 신청자가 취소할 수 있다. `PENDING` 7일 경과 시 `EXPIRED`, 재신청 가능 |
| 승인 심사 | `APPROVAL` 스터디의 `LEADER`·`MANAGER`는 신청자의 학습 프로필(공개 항목)을 확인하고 승인·거절한다. |
| 가입 방식 변경 | `LEADER`만 변경한다. `INSTANT → APPROVAL`은 언제든 가능하며 이후 신청부터 적용한다. `APPROVAL → INSTANT`는 `PENDING` 신청이 남아 있으면 `STUDY_PENDING_APPLICATIONS_EXIST`(409) |
| 모집 상태 | 정원이 차면 `ACTIVE`(모집 마감)로 자동 전이하고, 결원이 생기면 스터디장 설정에 따라 `RECRUITING`으로 되돌린다. |
| 역할 | `LEADER`(1명) / `MANAGER`(최대 2명) / `MEMBER`. 스터디장 정보의 원천은 `study_memberships.role` 하나이며 `studies`에 스터디장 컬럼을 두지 않는다. "스터디당 `APPROVED` 상태의 `LEADER`는 1명"을 DB 유일 제약(생성 컬럼 `leader_key = IF(role = 'LEADER' AND status = 'APPROVED', study_id, NULL)`에 유일 인덱스)으로 강제한다. 위임은 기존 `LEADER` 강등 → 대상 승격 순서로 한 트랜잭션에서 처리한다. |
| 권한 | 문제집 배정·모의 코테 생성·가입 승인·공지 작성/고정·게시판 관리·강제 탈퇴는 `LEADER`·`MANAGER`. 기본 정보·가입 방식 변경, 운영진 임명·해제, 스터디장 위임, 종료는 `LEADER`만 가능 |
| 탈퇴 | `MEMBER`·`MANAGER`는 언제든 탈퇴(`LEFT`)할 수 있다. `LEADER`는 다른 구성원에게 위임하기 전에는 탈퇴할 수 없다(`STUDY_LEADER_DELEGATION_REQUIRED`, 409). 유일한 구성원이면 스터디를 종료한 뒤 탈퇴한다. |
| 강제 탈퇴 | `LEADER`·`MANAGER`가 사유를 남기고 `REMOVED` 처리할 수 있다. `MANAGER`는 `LEADER`·다른 `MANAGER`를 강제 탈퇴시킬 수 없다. 같은 스터디 재가입은 승인이 필요하다. |
| 종료 | 스터디는 자동 종료되지 않고 `LEADER`가 직접 종료한다. 종료 전에 `SCHEDULED` 시험은 취소하고, `IN_PROGRESS` 시험은 `CLOSED`가 되어야 한다. 예정·진행 중 시험이 남아 있으면 종료를 차단한다. `CLOSED` 시험이 아직 `FINALIZED` 전이어도 종료를 막지 않으며, 스터디 종료 후에도 채점과 결과 확정은 계속 진행한다. `CLOSED` 스터디는 신규 가입·새 활동 생성이 불가하고, 게시글·문제집·기록을 읽기 전용으로 보존한다. |
| 커뮤니티 | 게시글·댓글은 해당 스터디 `APPROVED` 구성원만 조회·작성한다. 작성자는 본인 글을 수정·삭제하고, 운영진은 공지를 작성·상단 고정하며 부적절한 글을 숨길 수 있다. 탈퇴 후에는 조회 권한이 사라진다. |

### 7.1 문제집·진행률

| 항목 | 정책 |
| --- | --- |
| 구성 | 문제집은 `scope = GENERAL`·`visibility = PUBLIC` 문제 1개 이상으로 구성하며, 태그 단위로 묶는다(태그 기준은 §4와 동일). 기본 주 5문제, 스터디별로 조정한다. 생성 시점에 문제 선택 API가 반환한 `problemRevisionId`를 `assignment_problems.assigned_revision_id`에 기록한다. 기록한 회차는 배정 당시 문제를 확인·표시하는 용도이며, 진행 인정은 `problem_id` 기준으로 회차와 무관하게 판정한다. |
| 문제 비공개 전환 | 문제집에 포함된 문제가 `PRIVATE`로 전환되면 해당 문제를 `EXCLUDED`로 표시하고 진행률 분모에서 제외한다. 이미 인정된 기록은 삭제하지 않는다. 다시 `PUBLIC`이 되면 `ACTIVE`로 복귀한다. 전환은 `ProblemStateChanged` 이벤트로 반영한다. |
| 기간 | 시작 시각은 필수, 마감 시각은 선택이다. 마감을 지정할 때 기본값은 시작 + 7일이다. 마감이 없으면 기간 제한 없이 진행한다. |
| 인정 기준 | `PRACTICE` 문맥 제출의 `AC`만 인정한다. 시험·대회·진단 제출은 인정하지 않는다. `study-service`는 `PRACTICE` 문맥의 `SubmissionJudged`를 판정과 무관하게 모두 소비한다. `AC`는 인정·복제본 갱신에, `AC`가 아닌 판정은 해당 제출이 인정 근거였는지 확인해 재계산하는 데 사용한다. 다른 문맥의 채점 이벤트는 멱등 기록만 남기고 반영하지 않는다. |
| 완료 유형 | `PRE_SOLVED`(문제집 시작 전 AC, 기존 풀이 인정 옵션이 켜진 경우) / `ON_TIME`(시작~마감 사이 AC, 마감이 없으면 모두 `ON_TIME`) / `LATE`(마감 후 AC). 마감 후에도 제출과 인정은 계속된다. 판정 시각은 채점 완료 시각이나 이벤트 도착 시각이 아니라 제출 접수 시각(`submittedAt`)이다. 완료 유형은 `(제출 접수 시각, 문제집 시작 시각, 마감 시각, 기존 풀이 인정 옵션)`만으로 계산하며, 이벤트 도착 순서와 무관하게 같은 결과를 낸다. 기존 풀이 인정 옵션이 꺼져 있으면 시작 전 AC는 인정하지 않는다. |
| 기존 풀이 인정 | 문제집 옵션(기본 켬). `study-service`는 `SubmissionJudged`로 회원별 `PRACTICE` AC 복제본 `member_ac_replicas`(회원·문제·제출 ID·제출 접수 시각·채점 회차)를 제출 단위로 유지한다. 최초 AC는 유효한 복제본 중 제출 접수 시각이 가장 이른 행이다. ① 문제집이 `SCHEDULED`일 때 도착한 이벤트는 복제본만 갱신한다. ② `AssignmentLifecycleScheduler`가 `SCHEDULED → OPEN`으로 전이하는 트랜잭션에서 복제본을 조회해 `PRE_SOLVED` 기록을 일괄 생성한다. ③ `OPEN` 이후 도착한 이벤트는 완료 유형 계산으로 바로 반영한다. 복제본이 의심되면 `judge-service` 내부 API(§9.1)로 회원별 `PRACTICE` AC 목록을 받아 재구성하는 관리자 절차를 둔다. |
| 진행 기록 | `(assignment_id, member_id, problem_id)` 유일 제약으로 1건만 기록한다. 같은 문제 AC가 여러 번 와도 진행률은 1회 증가하며, 더 이른 유형(`PRE_SOLVED` > `ON_TIME` > `LATE`)을 유지한다. |
| 재채점 반영 | 인정 근거가 된 제출이 재채점으로 AC가 아니게 되면, 다른 AC가 있으면 그 제출로 근거와 유형을 다시 계산하고 없으면 인정을 취소한다. `assignment_progress`는 인정 근거 `submission_id`와 반영한 `judge_attempt`를 저장하고, 저장된 회차보다 큰 이벤트만 반영한다. 재채점된 제출의 `member_ac_replicas` 행은 무효 처리하며, 재계산은 남은 유효 복제본 중 접수 시각이 가장 이른 AC로 한다. |
| 진행률 | ① 전체 진행률 = 인정 문제 수 / 배정 문제 수 ② 기한 내 완료율 = (`PRE_SOLVED` + `ON_TIME`) / 배정 문제 수. 멤버별·스터디 평균을 제공한다. |
| 과제 상태 | 멤버별 `NOT_STARTED → IN_PROGRESS → COMPLETED`. 마감 시 미완료는 `INCOMPLETE`이며, 이후 전부 인정되면 `COMPLETED`(지각 포함)로 전이한다. |
| 미달 알림 | 마감 24시간 전 미완료 멤버에게 알림. 연속 2회 `INCOMPLETE` 멤버는 운영진에게 알림(자동 강퇴는 하지 않음) |
| 가입 시점 | 문제집 진행 중 가입한 멤버도 해당 문제집 대상에 포함한다. 가입 승인 트랜잭션에서 해당 스터디의 `SCHEDULED`·`OPEN` 문제집을 모두 조회해 멤버별 과제 상태(`assignment_member_status`, `NOT_STARTED`)를 생성하고, `OPEN` 문제집은 `member_ac_replicas`를 기준으로 문제별 진행 기록(`assignment_progress`)도 함께 생성한다. 가입 트랜잭션과 개설 스케줄러는 모두 유일 제약 기반 upsert로 기록하므로 실행 순서와 무관하게 1건만 남는다. `StudyMemberJoined` 이벤트 소비로 처리하지 않는다. |
| 후속 문제집 | 문제집 종료 후 멤버들의 미해결 문제를 후보로 새 문제집을 만들 수 있다. |

## 8. AI 정책

### 8.1 단계별 힌트

| 항목 | 정책 |
| --- | --- |
| 단계 | 1단계 접근 방향(알고리즘 분류·관찰 포인트) → 2단계 핵심 아이디어 → 3단계 풀이 절차(의사코드 수준). 앞 단계를 받은 뒤에만 다음 단계를 요청할 수 있다(`HINT_LEVEL_SKIPPED`, 409). |
| 대상 | `scope = GENERAL`·`visibility = PUBLIC` 문제만. 대회 전용 문제는 대회 종료 전 제외 |
| 답안 노출 금지 | 어떤 단계에서도 실행 가능한 코드를 제공하지 않는다. 응답은 정해진 JSON 스키마(단계·본문)로 받고, 코드 블록·언어 문법 패턴이 감지되면 1회 재생성, 다시 감지되면 폴백으로 대체한다. |
| 입력 범위 | 1차 범위에서 힌트 입력은 문제 본문·태그·단계뿐이다. 사용자 자유 입력과 사용자 코드는 넣지 않는다(프롬프트 인젝션 표면 최소화). 코드 기반 피드백은 P3 후보 |
| 시험·대회 중 차단 | 사용자가 참가 중인 시험·대회에 포함된 문제는 `HINT_BLOCKED_DURING_EXAM`(403)으로 거절한다. <br>① 원천: `study` 스키마의 차단 복제본 `hint_block_replicas`(회원·시험 참조(`EXAM:{id}` / `CONTEST:{id}`)·문제·시작 시각·종료 시각)를 둔다. 유일 제약은 `(회원, 시험 참조, 문제)`다. <br>② 생성: 참가 등록 이벤트를 받으면 해당 참가자와 시험 문제 목록으로 행을 만든다. 미입장(`ABSENT`) 참가자도 차단 대상에 포함한다.  <br>③ 판정: `시작 시각 <= 현재 < 종료 시각`인 행이 있으면 차단한다. 차단 여부를 시각으로 판정하므로 시작 이벤트 지연의 영향을 받지 않는다.  <br>④ 해제: 종료·취소 이벤트를 받으면 해당 시험 참조의 행을 삭제한다. 이벤트가 유실돼도 종료 시각 + 10분이 지난 행은 차단에 쓰지 않는다. <br>⑤ 이중 확인: 요청 접수 시점과 `READY` 전이 직전에 모두 확인한다. 전달 직전 차단되면 `BLOCKED`로 전이하고 일일 횟수를 차감하지 않는다. <br>⑥ 장애: 복제본 조회가 실패하면 거절한다(fail-closed). |
| 차단 적용 화면 | 차단은 시험 화면뿐 아니라 일반 문제 풀이 화면의 힌트 요청에도 똑같이 적용한다. |
| 진단 중 차단 | 진단이 진행 중인 사용자는 모든 문제의 힌트를 사용할 수 없다(§8.3). 판정 경로는 확정 필요. |
| 요청 제한 | 1인 하루 20회. 초과 시 `HINT_DAILY_LIMIT_EXCEEDED`(429). 캐시 적중 응답도 횟수에 포함한다. |
| 비동기 처리 | 요청은 즉시 `202`로 접수하고, 생성 완료 시 `HintReady` 알림으로 전달한다. |
| 캐시 | `(problem_revision_id, level)` 기준으로 캐시한다. 문제의 새 회차가 공개되면 무효화한다. |
| 타임아웃·폴백 | 15초 초과·LLM 장애·가드레일 실패 시 문제 태그 기반 정적 힌트를 제공하고 폴백 여부를 응답에 표시한다. 연속 실패 시 서킷브레이커를 연다. |
| 이력 | 힌트 사용 이력(문제·단계·시각·폴백 여부)을 기록한다. 힌트 사용 여부는 성취도 산정에 반영한다(§8.3). |
| 평가셋 회귀 | 힌트 평가셋(팀 전원 분담 작성)으로 정답 코드 노출·단계 위반·시험/진단 중 응답을 검사한다. 프롬프트·모델 변경 PR은 평가셋 통과가 필수다. |
| 운영 배포 조건 | 힌트 기능은 가드레일(응답 스키마 강제·코드 패턴 감지와 재생성·폴백·시험 중 차단)과 함께만 운영 환경에서 활성화한다. 평가셋 초판(최소 10문제 × 3단계) 통과 전에는 스테이징에서만 활성화한다. 기능 토글로 운영 중 즉시 비활성화할 수 있어야 한다. |

### 8.2 스터디 추천

| 항목 | 정책 |
| --- | --- |
| 이용 조건 | 학습 프로필(목표·선호 언어·활동 시간대)을 입력한 사용자에게 규칙 기반 추천을 제공한다. 진단이나 승급으로 태그 레벨이 정해지면 추천에 반영한다. 프로필이 없는 사용자에게는 오류 대신 인기순 목록과 프로필 입력 안내를 함께 반환한다. 학습 프로필 값은 `LearningProfileUpdated` 복제본을 사용하며, 저장된 프로필 버전보다 작거나 같은 이벤트는 무시한다. |
| 추천 대상 | `RECRUITING` 상태이고 정원이 남았으며 사용자가 이미 속하지 않은 스터디 |
| 1차 방식(규칙, P2) | 목표 일치, 태그 레벨 차이, 선호 언어, 활동 시간대 겹침을 가중합으로 점수화한다(가중치와 태그 레벨 집계 방식 확정 필요). |
| 2차 방식(임베딩, P3) | 스터디 목표 문구와 사용자 목표 문구의 임베딩 유사도를 점수에 더한다. 호출 실패 시 규칙 점수만 사용한다. |
| 콜드 스타트 | 프로필이 없거나 추천 점수 대상 스터디가 부족하면, `RECRUITING` 상태이고 정원이 남은 스터디를 최근 7일 활동(문제집 진행·게시글) 수 → 현재 인원 순으로 정렬해 제공한다. 추천 설명에는 "최근 활동이 많은 스터디"처럼 규칙 추천과 구분되는 근거를 표시한다. |
| 추천 설명 | 모든 추천에 근거(예: "목표 일치, 태그 레벨 비슷함")를 함께 보여준다. |
| 조건 수정 | 사용자는 추천 조건을 바꿔 다시 조회할 수 있다. |
| 결과 없음 | 추천 결과가 없거나 만족스럽지 않으면 신규 스터디 생성을 안내한다. 비슷한 사용자 수를 근거로 한 생성 제안은 P3 |
| 자동 배정 금지 | 시스템은 사용자를 스터디에 임의로 배정하거나 스터디를 자동 생성하지 않는다. 가입은 사용자가 결정한다. |
| 갱신 | 추천 결과는 하루 1회 갱신하고, 학습 프로필 변경 시 즉시 재계산한다. |

### 8.3 태그별 진단·레벨 갱신

> 기준 문서: 진단 테스트 및 실력 갱신 설계(2026.10.01)
> 

**레벨 체계**

| 항목 | 정책 |
| --- | --- |
| 레벨 단위 | 레벨은 사용자 전체가 아니라 **태그별**로 관리한다. 한 태그는 Lv.3, 다른 태그는 Lv.1일 수 있다. 사용자는 관심 있는 태그만 이용해도 된다. |
| 태그 상태 | `Lv.0`(미시작·첫 진단 응시 중) → `Lv.1`/`Lv.2`/`Lv.3` → 마스터 |
| 진입 선택 | 태그에 처음 진입할 때 진단 응시와 Lv.1 시작 중 하나를 고른다. 건너뛰어도 쿨타임을 걸지 않으며, 마이페이지·문제 목록에 "진단 테스트로 레벨 올리기" 안내를 상시 노출한다. |
| 문제 접근 제한 | 태그별로 자기 레벨에 해당하는 난이도까지만 연습 문제를 풀 수 있다. `Lv.1`은 난이도 1, `Lv.2`는 1~2, `Lv.3`·마스터는 1~3이다. 진단 중에는 레벨과 무관하게 출제된 문제를 푼다. 스터디·모의 코테의 예외 적용 여부는 확정 필요. |
| 레벨 상승 경로 | ① 단계별 승급(연습 문제 해결) ② 진단 테스트 (재)응시 결과가 현재 레벨보다 높은 경우 |

**진단 테스트**

| 항목 | 정책 |
| --- | --- |
| 응시 조건 | 태그 레벨이 `Lv.0`·`Lv.1`·`Lv.2`이면 응시할 수 있다. `Lv.3`·마스터는 응시 대상이 아니다. 같은 태그에서 진행 중인 진단이 있으면 새로 시작할 수 없다. |
| 쿨타임 | 태그별 첫 응시는 쿨타임 없이 응시한다. 이후는 직전 진단 종료 시각 기준 3일 쿨타임을 태그별로 계산한다. 건너뛰기는 쿨타임을 걸지 않는다. 채점 서버 장애로 `FAILED`가 발생한 응시에도 쿨타임을 적용하지 않는다. |
| 출제 | 해당 태그의 난이도 1·2·3 공개 문제 중 무작위로 1문항씩, 총 3문항. 연습에서 이미 푼 문제가 출제되어도 된다. |
| 제한 시간 | 총 60분. 문항별 기준 시간은 두지 않고 사용자가 순서와 시간을 배분한다. 남은 시간은 서버 시각 기준으로 표시한다. |
| 진행 중 이탈 | 작성 중인 코드는 서버 Draft와 LocalStorage에 이중 저장한다(§5.3과 같은 규칙). 문제 뷰어를 나가거나 브라우저를 종료해도 진단은 계속 진행되며, 제한 시간 안에 재진입하면 남은 시간으로 이어서 응시한다. |
| 제출 | 문항별로 제한 시간 안에 여러 번 제출할 수 있고, 문항별 최종 제출을 채점 결과로 반영한다. 제출 문맥은 `context = DIAGNOSIS`다. |
| 종료 | ① 사용자가 [최종 제출]을 누른 시각 ② 제한 시간 만료(시작 + 60분) 중 먼저 오는 시점에 종료한다. 만료는 스케줄러가 종료 처리하고 마지막 제출 이후 변경된 Draft를 자동 제출한다. 종료 이후의 저장·제출은 거절한다. |
| 응시 기록 | 시작한 진단은 제출하지 않아도 제한 시간 만료 시 자동 종료되어 응시 1회로 기록된다. |
| 힌트 | 진단 중에는 힌트를 사용할 수 없다(§8.1). |
| 집계 제외 | 진단 제출은 제출 이력에 표시하지만 승급 집계(해결 문제 수·성취도)에 포함하지 않는다. 진단에서 푼 문제를 이후 연습에서 다시 풀면 그 연습 제출은 승급 집계에 포함한다. |
| 결과 → 레벨 | 정답(`AC`)을 받은 문항 중 가장 높은 난이도를 레벨로 한다. 난이도 3 정답 → `Lv.3`, 난이도 2 정답·3 오답 → `Lv.2`, 난이도 1만 정답 또는 모두 오답 → `Lv.1`. 제한 시간 안에 한 번이라도 정답을 받은 문항을 정답으로 본다. 진단으로 마스터는 받을 수 없다. |
| 재응시 하향 금지 | 재응시 결과가 현재 레벨보다 낮으면 현재 레벨을 유지한다(`max(현재 레벨, 진단 결과)`). 결과 점수는 이력으로 보여준다. |

**점수·성취도**

| 항목 | 정책 |
| --- | --- |
| 문항 점수 | 난이도 1 → 1점, 난이도 2 → 2점, 난이도 3 → 3점. 힌트를 사용한 정답은 각 점수의 1/2점으로 계산한다. |
| 성취도 | `성취도(%) = 획득 점수 ÷ 총 문항 점수 × 100`. 누적으로 계산하며 누적 기간 제한은 확정 필요. |
| 반영 범위 | 채점 완료(`COMPLETED`) 상태의 제출만 반영한다. 채점 전 제출은 성취도 계산에서 제외하고 "채점 중"으로 표시한다. |
| 성취도 구간 | 잘함 80% 이상 / 보통 60~79% / 부족 0~59% |
| 약점 기준 | 성취도 부족 구간(0~59%)에 해당하는 태그를 약점으로 분류한다. |

**단계별 승급**

| 승급 | 기준 |
| --- | --- |
| Lv.1 → Lv.2 | 해당 태그 난이도 1 문제 5개 해결(AC) + 성취도 60% 이상 |
| Lv.2 → Lv.3 | 해당 태그 난이도 2 문제 6개 해결(AC) + 성취도 70% 이상 |
| Lv.3 → 마스터 | 해당 태그 난이도 3 문제 5개 해결(AC) + 성취도 65% 이상 (배지) |
- 해결 문제 수와 성취도는 연습(`PRACTICE`) 제출만 집계한다.
- 성취도 조건은 힌트 의존도를 거르는 역할을 한다.
    - (예: 5문제를 모두 힌트로 풀면 성취도 50%로 긍습하지 못한다)
- 승급 판정은 `SubmissionJudged`(`PRACTICE`)를 받을 때마다 수행한다.
- 기준값(문제 수·성취도)은 설정값으로 관리하고, 실운영 결과를 보고 조정한다.

**갱신·재채점 처리**

| 항목 | 정책 |
| --- | --- |
| 재계산 원칙 | 레벨은 저장된 값에서 증감하지 않고 현재 데이터로 매번 다시 계산한다. `level = max(진단 결과들)`에서 시작해 단계별 승급 기준을 차례로 적용한다. 이벤트 도착 순서·중복과 관계없이 같은 결과가 나온다. |
| 재채점 중 | 재채점 중인 제출은 새 결과가 도착할 때까지 직전 회차의 결과를 유지한다. "채점 중 제외" 규칙은 최초 채점에만 적용한다. |
| 재채점 반영 | 재채점 결과(더 큰 `judgeAttempt`)가 도착하면 해당 제출의 반영 결과를 최신 회차로 교체하고, 해당 (회원, 태그, 난이도)의 성취도와 태그 레벨을 처음부터 재계산한다. 이전 점수를 빼고 새 점수를 더하는 차분 방식은 쓰지 않는다. |
| 순서 역전 | 저장된 회차보다 작거나 같은 `judgeAttempt`의 결과는 무시한다. |
| 이력 보존 | 이전 판정은 물리 삭제하지 않는다. `judge-service`의 회차 이력으로 보존하고, 레벨·성취도 산정에는 최신 회차만 사용한다. |
| 레벨 하향 | 재채점 재계산으로 레벨이 내려갈 수 있다. 진단 재응시로는 내려가지 않는다. 레벨이 바뀌면 승급 또는 하향 알림을 보낸다. |
| 처리 순서 | `member-service`가 단일 트랜잭션에서 ① `processed_events`로 중복 이벤트 제거 ② 복제본 행의 `judgeAttempt` 비교 ③ 복제본 행을 최신 회차 결과로 교체 ④ 해당 (회원, 태그, 난이도) 성취도·레벨 재계산 ⑤ 레벨이 바뀌었으면 알림 이벤트를 Outbox에 기록한다. |
| 근거 조회 | 사용자는 태그별 현재 레벨과 최근 갱신 근거(어떤 제출로 얼마나 바뀌었는지)를 조회할 수 있다. |

**레벨 알림**

## 9. 이벤트·알림·연동·운영 정책

### 9.1 이벤트·정합성

| 항목 | 정책 |
| --- | --- |
| 발행 | 상태 변경과 Outbox 기록은 같은 DB 트랜잭션에서 수행한다. 트랜잭션 밖에서 메시지를 직접 발행하지 않는다. |
| 이벤트 형식 | 공통 헤더는 `eventId`(UUID), `eventType`, `schemaVersion`(메시지 형식 버전), `occurredAt`, `aggregateId`, `correlationId`다. 순서 비교가 필요한 값은 페이로드에 도메인 이름으로 둔다(`judgeAttempt`, `examRevision` 등). 자연스러운 순번이 없는 이벤트는 순번 필드를 별도로 정의한다. |
| 식별자 타입 | 모든 이벤트 페이로드의 ID 필드는 문자열로 쓴다. DB PK가 `bigint`라서 JS 클라이언트에서 Number 정밀도 손실이 생길 수 있다. |
| 시간 형식 | 시간 필드는 오프셋 포함 ISO-8601, 마이크로초 자릿수로 쓴다. |
| 전달 보장 | 최소 1회 전달. 순서는 보장하지 않는다. |
| 멱등 소비 | 소비자는 `processed_events(event_id)` 유일 제약 기록과 반영을 같은 트랜잭션에서 수행한다. 이미 기록된 이벤트는 반영 없이 성공 처리한다. |
| 순서 역전 | 채점 결과 이벤트(`SubmissionJudged`·`ExamSubmissionJudged`·`ContestSubmissionJudged`)를 소비할 때 같은 `submissionId`에 대해 저장된 `judgeAttempt`보다 작거나 같은 회차의 결과는 반영하지 않는다. 다른 이벤트는 순서 비교가 필요한 경우 해당 이벤트 계약에 순서 값을 정의한다. |
| 소비 실패 | 재시도 후에도 실패한 메시지는 큐별 DLQ로 격리하고 운영 알림을 보낸다. 재처리는 관리자 절차로만 한다. |
| 스키마 변경 | 필드 추가는 하위 호환으로만 한다. 필드 삭제·의미 변경은 새 `eventType` 또는 `schemaVersion`으로 발행하고 소비 서비스 담당자 승인을 받는다. |
| 데이터 소유 | 다른 서비스의 DB·스키마에 직접 접근하지 않는다. 필요한 값은 API 조회 또는 이벤트 복제본을 쓴다. |
| 동기 호출 | 서비스 간 동기 호출은 타임아웃(2초)과 서킷브레이커를 적용한다. 검증 목적 조회가 실패하면 요청을 거절한다(fail-closed). |
| 복제본 재동기화 | 복제본이 의심되면 소유 서비스의 내부 조회 API로 재구성하는 관리자 절차를 둔다. 회원별 `PRACTICE` AC 복제본은 `judge-service` 내부 API `GET /internal/v1/submissions/accepted?context=PRACTICE&userId=&after=&size=`(커서 페이징)로 재구성한다. 반환 필드는 `submissionId`·`problemId`·`submittedAt`·`judgeAttempt`이며, AC만 반환하므로 판정 필드는 두지 않는다. 회원이 없으면 빈 목록을 반환한다. |

### 9.2 알림

| 항목 | 정책 |
| --- | --- |
| 알림 종류 | 일반 풀이 채점 결과, 채점 처리 실패·재처리 예정, 시험 시작 임박·결과 공개·일정 변경·취소, 대회 시작·결과 공개·취소, 스터디 가입 승인·거절, 문제집 배정·마감 임박, 문제집 연속 미완료(운영진), 스터디 강제 탈퇴, 태그 레벨 변경(진단 결과·승급·마스터·재채점 하향·쿨타임 해제), 힌트 준비 완료, GitHub 동기화 실패 |
| 채점 알림 적용 범위 | `PRACTICE` 제출은 채점 완료 시 판정 결과를 알린다. `EXAM`·`CONTEST` 제출은 건별 채점 완료 알림을 보내지 않고 각 문맥의 결과 공개 정책에 따라 화면에서 확인한다. 채점 처리 실패로 재처리가 필요하면 문맥과 무관하게 알림을 보낸다. |
| 시험·대회 알림 시점 | 시험 시작 임박은 시작 전에, 대회 시작은 `RUNNING` 전이에 알린다. 시험 `CLOSED`·대회 `ENDED` 전이에는 별도 종료 알림을 보내지 않는다. 결과 공개 알림은 각각 `FINALIZED` 전이에 보낸다. 시험 일정 변경·취소는 등록자에게 알린다. |
| 생성 책임 | 도메인은 이벤트만 만들고 `notification-service`가 수신자·문구·이동 경로를 정해 알림을 생성한다. |
| 중복 방지 | `(source_event_id, user_id, type)` 유일 제약. 같은 이벤트가 재전달되어도 알림은 1건만 생성한다. |
| 수신 설정 | 종류별 수신 여부를 설정할 수 있다. 채점 결과는 끌 수 없다(실시간 결과 표시에 필요). |
| 전달 | 저장 후 SSE로 전달한다. 연결이 없으면 저장만 하고 재연결 시 `Last-Event-ID` 이후 미읽음을 재전송한다. |
| 읽음 | 개별·전체 읽음 처리. 본인 알림만 조회·변경하고 미읽음 개수를 제공한다. |
| 장애 분리 | 알림 실패가 제출·채점·시험 종료 처리를 막지 않는다. 예약 알림이 늦어져도 시험 시간 판정에는 영향이 없다. |

### 9.3 GitHub 연동

| 항목 | 정책 |
| --- | --- |
| 인가 | 로그인과 별도로 사용자가 선택한 저장소 1개에 대한 쓰기 권한만 인가받는다(GitHub App 설치 여부 1주차 결정). |
| 토큰 보관 | AES-GCM으로 암호화해 저장하고, 암호화 키는 Secrets로만 주입한다. 토큰은 로그·응답에 출력하지 않는다. |
| 동기화 대상 | `PRACTICE` 문맥의 `AC` 제출만. 시험·대회·진단 제출과 비공개 대회 문제는 동기화하지 않는다. |
| 코드 조회 | Sync Job 실행 시 `integration-service`가 `judge-service` 내부 API로 제출 코드를 조회한다(서비스 계정 인증, 외부 비공개). |
| 저장 구조 | `{난이도}/{문제번호}-{문제명}/{언어별 파일}` + 문제 정보 `../../../README.md`. 같은 문제 재AC는 같은 경로를 갱신하는 새 커밋으로 남긴다. |
| 중복 방지 | Sync Job은 `submission_id` 유일 제약으로 1건만 생성한다. |
| Rate Limit | 응답 헤더의 잔여 호출 수가 기준 이하이거나 403·429를 받으면 `RATE_LIMITED`로 전이하고 초기화 시각 이후 재시도한다. |
| 실패 | 재시도 5회 초과 시 `FAILED`, 사용자에게 알림. 권한 만료(401)면 연동을 `DISCONNECTED`로 바꾸고 재인가를 안내한다. |
| 연동 해제 | 토큰을 폐기·삭제하고 대기 중인 Sync Job을 `CANCELED`로 전이한다. 이미 커밋된 파일은 삭제하지 않는다. |

### 9.4 운영·보안 정책

| 항목 | 정책 |
| --- | --- |
| 채점 서버 격리 | Judge0는 별도 EC2에서 실행한다. 보안 그룹 인바운드는 `judge-service`만 허용하고 퍼블릭으로 API를 노출하지 않는다. 내부 통신은 프라이빗 IP |
| 실행 중 네트워크 | 사용자 코드 실행 중 네트워크를 비활성화한다. |
| 메타데이터 차단 | 채점 EC2에는 IAM Role을 부여하지 않고, IMDSv2 강제·홉 제한 1·`169.254.169.254` 차단을 적용한다. 샌드박스에는 AWS 자격 증명·서비스 비밀값을 전달하지 않는다. |
| 자원 제한 | 프로세스 수·파일 크기·출력 크기·실행 시간·메모리 제한을 적용한다. 출력이 제한을 넘으면 `RE`(출력 초과)로 처리한다. |
| 악성 코드 검증 | 네트워크 접근·메타데이터 조회·fork bomb·대용량 출력·파일 쓰기 테스트 세트를 배포 전 검증에 포함한다. |
| 숨김 데이터 | 숨김 테스트케이스·정답 코드·타인 제출 코드는 권한 검증 없이 반환하는 API를 두지 않는다. |
| 내부 API | 서비스 간 내부 API(`/internal/**`)는 Gateway 라우팅에서 제외하고 Compose 내부 네트워크에서만 접근한다. 서비스 계정 인증을 적용하며, `GET /internal/v1/submissions/accepted`(회원별 `PRACTICE` AC 목록)와 제출 코드 조회 API가 여기에 속한다. |
| 관리자 감사 로그 | 각 서비스가 자기 도메인의 감사 로그를 자기 DB에 기록한다. 전체 조회가 필요해지면 별도 분리를 검토한다. 문제 공개·승인·반려·비공개 전환, 재채점·DLQ 재처리, 시험·대회 재확정·0점 확정, 회원 정지·권한 변경, 스터디 강제 종료는 작업자·사유·변경 전후 값·시각을 기록한다. |
| 회원 탈퇴 전파 | `MemberWithdrawn` 수신 시: 표시 이름 익명화("탈퇴한 사용자"), GitHub 토큰 삭제·Sync Job 취소, 스터디 가입 `LEFT`·대기 신청 `CANCELED`, 알림 삭제, 공유 풀이 비공개, 스터디의 학습 프로필 복제본·추천 결과 삭제, 힌트 차단 복제본 삭제. 제출과 `member_ac_replicas`·스터디 진행 기록은 통계 보존을 위해 익명화 후 유지한다. |
| 상태 변경 | 상태 변경은 검증을 포함한 도메인 메서드로만 수행한다. 검증을 우회하는 setter성 메서드를 두지 않는다. |
| 스케줄러 | 상태 전이 스케줄러는 조건부 원자적 UPDATE로 수행하고, ShedLock으로 다중 인스턴스 중복 실행을 막는다. Outbox Relay는 중복 발행 방지에 `SELECT … FOR UPDATE SKIP LOCKED`를 쓰고, 만료 데이터 정리 배치만 ShedLock으로 1대만 실행한다. 서비스 재기동 시 밀린 작업은 시각 도달 여부로 판정해 따라잡는다. |
| 로깅 | 모든 요청·메시지에 `correlationId`를 전파해 로그에 남긴다. 제출 코드 본문·토큰·개인정보·요청 본문은 로그에 남기지 않는다. |
| 비밀값 | 코드·설정 파일에 저장하지 않고 GitHub Secrets·Parameter Store·환경 변수로 주입한다. 배포는 OIDC 임시 자격 증명을 쓴다. |
| 환경 분리 | 스테이징·운영은 DB·큐·버킷·비밀값을 분리하고 교차 접근을 차단한다. 운영 데이터 초기화·스테이징 복사는 허용하지 않는다. |
| 시간 기준 | 서비스·DB·API의 시간 기준을 `Asia/Seoul`로 통일하고 DB는 `DATETIME(6)`을 사용한다. |
| 환경 중지 | 중지는 신규 접수 차단 → 진행 중 시험·진단·채점·저장 완료 확인 → 실행기·API·DB 중지 순서로 한다. 완료를 확인할 수 없으면 중지를 보류한다. 진행 중인 사용자 시험은 강제로 중단하지 않는다. |
| 비용 | AWS 예산 알림(100,000원·140,000원·170,000원)을 설정하고, 실운영 기간 외에는 스테이징·채점 서버를 중지한다. |

## 10. 주요 상태 전이

| 도메인 | 상태 |
| --- | --- |
| 회원(`members`) | `ACTIVE ↔ SUSPENDED`, `ACTIVE / SUSPENDED → WITHDRAWN` |
| 문제 공개 상태(`problem.visibility`) | `PRIVATE ↔ PUBLIC`, `PRIVATE / PUBLIC → ARCHIVED` (공개된 수정 회차가 1개 이상일 때만 `PUBLIC`) |
| 문제 용도(`problem.scope`) | `GENERAL` / `EXAM_ONLY` (생성 시 결정) |
| 문제 수정 회차(`problem_revision`) | 공개된 회차는 수정하지 않고 새 회차를 만든다(`revision_number + 1`). 이전 회차는 이력으로 보존한다. (P2 검수 워크플로 도입 시: `DRAFT → IN_REVIEW → 승인 / REJECTED`, `REJECTED → DRAFT`) |
| 제출(`submissions`) | `QUEUED → JUDGING → COMPLETED`, <br>`JUDGING → RETRY_WAITING → JUDGING`(시스템 오류·임대 만료 회수), <br>`RETRY_WAITING / JUDGING → FAILED`(실행 시도 상한 초과), <br>`FAILED → QUEUED`(관리자 재처리), <br>`COMPLETED → QUEUED`(관리자 재채점, `judge_attempt + 1`) |
| 제출 판정(`submissions.verdict`) | `COMPLETED`일 때만 `AC / WA / TLE / MLE / RE / CE` 중 하나 |
| 채점 작업(`judge_jobs`) | `PENDING → RUNNING → SUCCEEDED`, <br>`RUNNING → RETRY_WAITING → RUNNING`(`try_count + 1`, 백오프 10→30초), <br>`RETRY_WAITING / RUNNING → FAILED`(`try_count` 3 초과) |
| 채점 실행 이력(`judge_job_runs`) | 실행 시도마다 1행 생성, 불변 이력 |
| Outbox(`outbox_events`) | `PENDING → PUBLISHED`, `PENDING → FAILED → PENDING`(재시도) |
| 시험(`exams`) | `SCHEDULED → IN_PROGRESS → CLOSED → FINALIZED`, <br>`SCHEDULED → CANCELED`, <br>`FINALIZED → FINALIZED`(관리자 재확정, 감사 로그) |
| 시험 참가자(`exam_participants`) | `REGISTERED → STARTED → FINISHED`(수동 종료·자동 제출 완료), <br>`REGISTERED → ABSENT`(종료 시까지 미입장), <br>`REGISTERED → CANCELED`(시작 전 참가 취소) |
| 시험 제출(`exam_submissions`) | `ACCEPTED → REQUESTED`(Outbox 발행) `→ JUDGED`(채점 결과 연결), `REQUESTED → FAILED`(연결된 제출 `FAILED`) |
| 대회(`contests`) | `SCHEDULED → RUNNING → ENDED → FINALIZED`, `SCHEDULED → CANCELED` |
| 스터디(`studies`) | `RECRUITING ↔ ACTIVE`, `RECRUITING / ACTIVE → CLOSED`(예정·진행 중 시험이 없을 때만) |
| 스터디 가입(`study_memberships`) | `PENDING → APPROVED / REJECTED / CANCELED / EXPIRED`, <br>`APPROVED → LEFT / REMOVED`(`INSTANT` 가입은 `APPROVED`로 바로 생성) |
| 스터디 역할(`study_memberships.role`) | `MEMBER ↔ MANAGER`, `LEADER ↔ MANAGER / MEMBER`(위임 시 기존 `LEADER` 강등 → 대상 승격 순서로 한 트랜잭션에서 교체, `leader_key` 유일 인덱스로 2명 저장 차단) |
| 문제집(`assignments`) | `SCHEDULED → OPEN → CLOSED`(마감 있음) / `SCHEDULED → OPEN`(마감 없음, 스터디 종료 시 `CLOSED`) |
| 과제 진행(`assignment_member_status`) | `NOT_STARTED → IN_PROGRESS → COMPLETED`, <br>`NOT_STARTED / IN_PROGRESS → INCOMPLETE`(마감), <br>`INCOMPLETE → COMPLETED`(지각 완료), <br>`COMPLETED → IN_PROGRESS / INCOMPLETE`(재채점으로 인정 취소) |
| 문제집 문제(`assignment_problems.status`) | `ACTIVE ↔ EXCLUDED`(문제 `PRIVATE` 전환·재공개) |
| 문제 진행(`assignment_progress.completion_type`) | `PRE_SOLVED / ON_TIME / LATE` (제출 접수 시각으로 계산, 더 이른 유형 유지, 재채점 시 남은 유효 AC로 재계산하거나 기록 삭제) |
| 진단 응시(테이블명·상태명 확정 필요) | `IN_PROGRESS → CLOSED`(최종 제출 또는 제한 시간 만료 + 자동 제출) `→ SCORED`(채점 종결 후 레벨 반영). 종료 이후의 저장·제출은 반영하지 않는다 |
| 태그 레벨(`member_tag_levels`) | `Lv.0 → Lv.1 / Lv.2 / Lv.3 → 마스터`. 진단 재응시로는 하향하지 않고(`max`), 재채점 재계산으로만 하향될 수 있다 |
| 힌트 요청(`hint_requests`) | `REQUESTED → GENERATING → READY` / `GENERATING → FALLBACK`(타임아웃·장애·가드레일 실패) / `REQUESTED → BLOCKED`(시험·진단 중·제한 초과) / `GENERATING → BLOCKED`(전달 직전 재확인에서 차단, 일일 횟수 미차감) |
| GitHub 연동(`github_connections`) | `CONNECTED → DISCONNECTED`(해제·권한 만료), `DISCONNECTED → CONNECTED`(재인가) |
| GitHub Sync Job(`github_sync_jobs`) | `PENDING → RUNNING → SUCCEEDED`, <br>`RUNNING → RETRY_WAITING → PENDING`, <br>`RUNNING → RATE_LIMITED → PENDING`, <br>`RETRY_WAITING → FAILED`(상한 초과), `PENDING / RETRY_WAITING → CANCELED`(연동 해제) |
| 알림(`notifications`) | `UNREAD → READ` |
- `submissions.status`와 `judge_jobs`의 상태는 다음처럼 대응한다. 두 값이 어긋나면 5분 주기 대사 배치의 복구 대상이다.
    - `QUEUED` ↔ `PENDING`
    - `RETRY_WAITING` ↔ `RETRY_WAITING`
    - `JUDGING` ↔ `RUNNING`(임대 유효)
    - `COMPLETED` ↔ `SUCCEEDED`
    - `FAILED` ↔ `FAILED`
- `exam_submissions.status = ACCEPTED`가 1분 넘게 머물면 Outbox 발행 실패로 보고 운영 알림을 보낸다.
- `exams.status = FINALIZED`인데 해당 시험에 비종결 제출이 있으면 정합성 위반이다.
