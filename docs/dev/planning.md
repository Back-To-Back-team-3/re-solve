## 1. 프로젝트 개요

### 1.1 서비스 소개

**Re:Solve는 문제 풀이 → 비동기 채점 → 스터디 학습 → 모의 코딩테스트로 이어지는, "혼자 푸는 곳이 아니라 같이 푸는 곳"을 지향하는 알고리즘 학습 플랫폼이다.**

개발자와 취업 준비생은 문제를 풀고 채점받는 것 외에도, 비슷한 실력과 목표를 가진 사람과 스터디를 꾸리고, 실제 기업 코딩테스트와 같은 조건(시간 제한·자동 제출·부분 점수)으로 연습해야 한다. 그러나 기존에는 문제 풀이 사이트, 커뮤니티 모집 글, 스터디장의 수작업 진도 집계가 각각 흩어져 있다.

Re:Solve는 이 흐름을 하나로 잇는다.

- 사용자가 제출한 임의의 코드를 **격리된 채점 서버**에서 안전하게 실행한다.
- 시험 마감처럼 제출이 몰리는 시점에도 **채점 요청을 유실 없이** 처리한다.
- 채점 결과는 이벤트로 전파되어 **스터디 진도·시험 순위·태그 레벨·알림·GitHub 기록**에 각각 자동 반영된다.
- 학습 수준은 전체 단일 등급이 아니라 **알고리즘 태그별 레벨**로 관리해, 부족한 태그를 보고 학습하도록 유도한다.

4차 프로젝트에서는 MSA 구조를 채택하고, 서비스 간 정합성을 분산 트랜잭션 대신 Transactional Outbox + 멱등 이벤트 소비로 맞춘다. 또한 시연용 데모가 아니라 약 1주일간 실제 사용자에게 서비스를 운영하고, 운영 중 관찰한 지표로 개선한다.

### 1.2 해결 과제

| 해결 과제 | 해결 방향 |
| --- | --- |
| 스터디원을 모을 때 실력·목표·활동 시간이 고려되지 않아 그룹 내 격차가 생기고, 모집 자체에 시간이 든다. | 학습 프로필(목표·태그 레벨·언어·활동 시간) 기반 **스터디 추천**과 추천 근거를 제공한다. |
| 자신이 어느 알고리즘에 약한지 모른 채 난이도만 올려 가며 푼다. | 태그별 **진단 테스트**와 **단계별 승급**으로 태그마다 레벨을 따로 관리하고, 성취도가 낮은 태그를 약점으로 보여준다. |
| 스터디장이 문제 선정·풀이 확인·진도 집계를 수작업으로 한다. | 스터디 문제집을 배정하면 **채점 결과 이벤트로 진도가 자동 집계**된다. 기존 풀이·기한 내·지각 완료는 **제출 접수 시각** 기준으로 구분하며, 이벤트 도착 순서·재채점과 관계없이 같은 결과를 낸다. |
| 문제를 풀어도 제한 시간 실전 연습으로 이어지기 어렵다. | 스터디 단위 **모의 코딩테스트**(서버 시각 판정·자동 저장·마감 자동 제출·부분 점수·순위)를 제공한다. |
| 사용자가 제출한 임의 코드는 서버를 공격할 수 있다(fork bomb, 네트워크·메타데이터 접근). | 채점 엔진(Judge0)을 **별도 인스턴스로 분리**하고 인바운드 차단·실행 중 네트워크 차단·IMDS 차단·자원 제한을 적용한다. |
| 채점은 수 초가 걸려 동기 처리하면 제출 API가 점유되고, 마감 직전 폭주 시 요청이 유실될 수 있다. | 제출은 접수 트랜잭션에서 **채점 작업(`judge_jobs`)을 함 DB 작업 테이블에 기록**하고 `202 Accepted`로 응답한 뒤, 실행기가 작업을 선점해 비동기 채점한다. 마감 판정은 채점 완료가 아니라 **서버 접수 시각** 기준이다. |
| 채점 결과 저장과 이벤트 발행 사이 장애로 진도·순위·알림이 어긋날 수 있다. | **Transactional Outbox**로 상태 변경과 이벤트 발행을 원자적으로 보장하고, 소비자는 **이벤트 ID 멱등 처리 + 채점 회차 비교**로 중복·역전을 막는다. |
| 채점 엔진 장애로 제출이 영구히 "채점 중"에 갇힐 수 있다. | 실행 시도 상한·지수 백오프·임대(lease) 만료 회수·장시간 `RUNNING` 작업 회수 스케줄러·DLQ 격리·관리자 재처리를 둔다. |
| 문제·테스트케이스가 수정되면 과거 제출과 진행 중 시험의 공정성이 깨진다. | 문제 수정 회차(`problem_revision`)를 불변으로 관리하고, 제출과 시험은 **특정 회차에 고정**한다. |
| 모의 코테 중 브라우저 종료·네트워크 단절로 작성 중인 코드를 잃을 수 있다. | 서버 Draft 자동 저장 + LocalStorage 이중 보관, `seq` 기반 저장 역전 방지, 마감 시 서버 최신 Draft 자동 제출을 적용한다. 진단 테스트도 같은 방식으로 복구한다. |
| 막힌 문제에서 정답 코드를 보는 것 외에 선택지가 없다. | LLM **단계별 힌트**를 제공하되 답안 노출 방지·시험/대회·진단 중 차단(시험 참가 복제본 기반, 요청·전달 시점 이중 확인, fail-closed)·요청 제한 가드레일을 적용한다. 가드레일 없이는 운영 환경에서 힌트를 활성화하지 않는다. |
| 여러 서비스로 나뉜 요청은 장애 지점을 찾기 어렵다. | Gateway에서 발급한 **Correlation ID**를 HTTP·메시지 전 구간에 전파한다. |

### 1.3 서비스 대상

- 코딩테스트를 준비하는 취업 준비생·부트캠프 수강생 (1차 실사용자: 팀원 및 부트캠프 동기·전 기수)
- 혼자서는 꾸준히 풀기 어려워 스터디 단위로 목표와 진도를 관리하고 싶은 학습자
- 스터디원을 모아 운영하고 모의 코테로 실력을 점검하려는 스터디장·동아리
- 문제를 출제·검수하고 채점 장애에 대응해야 하는 운영자(관리자)

### 1.4 주요 이용 시나리오

| 시나리오 | 사용자 행동 | 기대 결과 |
| --- | --- | --- |
| 가입·학습 프로필 | GitHub OAuth로 가입한다. 추천을 이용할 때 목표·선호 언어·활동 시간을 입력하고 진단 테스트를 푼다. | 맞춤 스터디 추천의 기초 데이터가 생긴다. 입력하지 않아도 일반 기능은 이용할 수 있다. |
| 진단·레벨 | 관심 태그에 처음 들어갈 때 진단 테스트 응시와 Lv.1 시작 중 하나를 고른다. | 응시하면 태그 레벨이 Lv.1~Lv.3으로 정해지고, 건너뛰면 Lv.1로 시작한다. 레벨에 해당하는 난이도까지 연습 문제를 푼다. |
| 일반 문제 풀이 | 난이도·태그·풀이 상태로 문제를 찾고, 코드를 실행(Run)해 본 뒤 제출한다. | 즉시 접수 응답을 받고, 채점 결과(AC/WA/TLE/MLE/RE/CE)와 시간·메모리를 실시간으로 확인한다. |
| 레벨 올리기 | 같은 태그의 연습 문제를 계속 푼다. | 해결 수와 성취도 기준을 채우면 다음 레벨로 승급하고 알림을 받는다. |
| 막혔을 때 | 단계별 힌트를 요청한다. | 정답 코드 없이 접근 방향 → 핵심 아이디어 → 풀이 절차를 단계적으로 안내받는다. |
| 스터디 찾기·가입 | 추천 스터디(추천 근거 포함)를 보거나 조건 검색 후 가입한다. 맞는 스터디가 없으면 조건을 초기값으로 새 스터디를 만든다. | 즉시 가입 또는 승인 대기 상태가 되고, 결과를 알림으로 받는다. |
| 스터디 과제 | 스터디장이 태그 단위 문제집을 배정하고, 스터디원이 문제를 푼다. | 정답 처리 결과가 이벤트로 반영되면 진행률이 자동 갱신되고, 마감 임박·미달 시 알림을 받는다. |
| 모의 코딩테스트 | 스터디장이 연 시험에 참가해 제한 시간 안에 여러 문제를 푼다. 중간에 브라우저가 꺼져도 다시 들어온다. | 작성 중인 코드가 복구되고, 마감 시 자동 제출되며, 종료 후 점수·순위를 확인한다. |
| 공개 대회 | 관리자가 연 대회에 참가해 실시간 순위표를 보며 푼다. | ICPC 방식 패널티로 공정하게 순위가 산정된다. |
| 풀이 공유·리뷰 | AC 코드를 스터디에 공유하고 다른 풀이와 Diff 비교, 라인 댓글을 남긴다. | 풀이 방식 차이를 비교하며 코드 리뷰를 주고받는다. |
| 풀이 기록 | GitHub 저장소를 연동한다. | 맞힌 코드가 정해진 구조로 자동 커밋된다. |
| 서비스 운영 | 관리자가 문제를 등록·관리하고, 실패한 채점 작업을 조회·재처리한다. | 장애로 멈춘 제출 없이 서비스가 유지되고, 모든 조치가 감사 로그로 남는다. |

| 힌트 가드레일 | 힌트 평가셋에서 정답 코드 노출 0건, 시험·진단 중 힌트 응답 0건 | 힌트 평가셋 회귀 |

## 3. 핵심 기능

### 3.1 사용자 흐름

**일반 풀이 흐름**

1. 사용자는 GitHub OAuth2로 로그인하고 JWT를 발급받는다. 가입 시 실력 진단은 강제하지 않는다.
2. Problem의 문제 목록에서 난이도·알고리즘 태그·풀이 상태·키워드로 문제를 찾는다. 연습으로 풀 수 있는 난이도는 해당 태그의 사용자 레벨까지다.
3. 선택한 문제의 설명·예제·함수 명세를 조회하고 언어를 선택해 코드를 작성한다. 작성 중인 코드는 브라우저에 자동 저장한다. 제출 전에 공개 테스트케이스나 직접 입력으로 코드를 실행(Run)해 볼 수 있다.
4. 클라이언트는 Judge에 `problemId`, 조회한 회차의 `problemRevisionId`, `language`, `sourceCode`를 제출한다. 요청에는 클라이언트가 생성한 `Idempotency-Key`를 포함한다.
5. Judge는 사용자 인증·제출 언어·코드 크기·제출 빈도를 검사하고, Problem의 사전 검증 API로 해당 회차의 문제 일치·채점 데이터 준비 상태를 확인하며 응답의 `scope=GENERAL`, `visibility=PUBLIC`을 검사한다. 새 수정 회차가 등록됐더라도 요청한 회차로 제출할 수 있다.
6. 검증을 통과하면 Judge는 제출(`QUEUED`)과 채점 작업(`judge_jobs`, `PENDING`)을 하나의 DB 트랜잭션으로 저장하고, `202 Accepted`와 `submissionId`를 반환한다. 일반 풀이 채점 요청은 SQS를 거치지 않는다.
7. 채점 실행기는 `SELECT … FOR UPDATE SKIP LOCKED`로 대기 작업을 동시 처리 수만큼 선점해 `RUNNING`으로 전환하고 임대(`lease_token`)를 잡는다. 제출에 고정된 문제 회차의 함수 명세·실행 제한·테스트를 조회해 테스트별로 Judge0에 실행을 요청하고, 받은 token으로 결과를 주기적으로 조회한다.
8. Judge0에는 실행 코드와 입력만 전달하고, 반환값의 타입·기대값 비교는 Judge가 수행한다. 모든 테스트를 평가한 뒤 최종 판정(`AC/WA/TLE/MLE/RE/CE`)·통과 수·시간·메모리를 저장하고 `COMPLETED`로 전환한다. 같은 DB 트랜잭션에서 `SubmissionJudged`를 Outbox에 기록한다. 실행 실패는 `try_count`를 올려 재시도하고, 상한(3회)을 넘으면 `FAILED`와 실패 이벤트를 기록한다.
9. 이벤트는 Outbox, SNS 토픽을 거쳐 각 소비 서비스의 SQS 큐로 전달된다. `SubmissionJudged`는 `PRACTICE` 전용, 시험·대회는 `ExamSubmissionJudged`·`ContestSubmissionJudged`로 분리 발행한다.
    - `problem-service`: 사용자별 문제 풀이 상태 갱신. 기존 해결 상태는 이후 오답 제출이나 문제 수정으로 초기화하지 않는다.
    - `notification-service`: 채점 완료·실패 SSE 알림
    - `study-service`: 배정 문제집 진행률 갱신
    - `member-service`: 태그별 성취도·레벨 갱신
    - `integration-service`: AC이고 연동 사용자이면 GitHub Sync Job 등록
    - `contest-service`: 시험·대회 제출이면 문맥별 이벤트로 점수·순위 갱신
10. 사용자는 제출 상태와 채점 결과를 조회한다. 일반 풀이가 시스템 장애로 최종 실패하면 오류를 안내하고 브라우저에 저장된 코드를 유지하며, 나중에 새 제출로 다시 시도할 수 있다. 막힌 문제에서는 단계별 힌트를 요청할 수 있고, 힌트는 비동기로 생성되어 알림으로 전달된다.

**진단·레벨 흐름**

1. 레벨은 사용자 전체가 아니라 알고리즘 태그별로 관리한다. 사용자는 관심 있는 태그를 골라 진입하며, 모든 태그를 이용할 필요는 없다.
2. 태그에 처음 진입하면 진단 테스트 응시와 Lv.1로 시작 중 하나를 고른다. 건너뛰어도 쿨타임이 걸리지 않고, 마이페이지·문제 목록에 재응시 안내가 상시 노출된다.
3. 진단은 해당 태그의 난이도 1·2·3 문제 중 무작위로 1문항씩, 총 3문항·60분으로 응시한다. 작성 중인 코드는 서버 Draft와 LocalStorage에 이중 저장되어 이탈 후 재진입해도 이어서 풀 수 있다.
4. 최종 제출을 누르거나 제한 시간이 만료되면 진단이 종료된다. 만료 시에는 스케줄러가 마지막 제출 이후 변경된 Draft를 자동 제출하고, 이후 저장·제출은 거절한다.
5. 정답을 받은 문항 중 가장 높은 난이도가 레벨이 된다. 재응시 결과가 현재 레벨보다 낮아도 레벨은 내려가지 않는다. 재응시 쿨타임은 종료 시각 기준 3일이다.
6. 같은 태그의 연습 문제를 풀어 해결 수와 성취도 기준을 채우면 단계별로 승급하고, Lv.3에서 기준을 채우면 마스터 배지를 받는다. 승급 판정은 `PRACTICE` 채점 결과 이벤트를 받을 때마다 수행한다.
7. 레벨이 오르거나 재채점으로 조정되면 SSE 알림으로 알린다.

**스터디 흐름**

1. 사용자는 모집 중인 스터디를 조건 검색하거나 추천 스터디(추천 근거 포함)를 본다. 학습 프로필이 있으면 규칙 기반 추천을, 없으면 최근 활동이 많은 스터디 목록과 프로필 입력 안내를 받는다. 진단으로 태그 레벨이 정해지면 추천에 반영된다.
2. 즉시 가입 또는 승인 가입으로 참여한다. 인원 제한·중복 신청·1인 참여 상한은 서버에서 검증한다. 가입이 승인되면 진행 중이거나 예정된 문제집에 바로 포함되고, 이미 푼 문제는 기존 풀이로 인정된다.
3. 맞는 스터디가 없으면 검색·추천 조건을 초기값으로 새 스터디를 만든다.
4. 스터디장·운영진이 태그 단위 문제집(공개 문제로 구성)을 배정하고, 기존 풀이 인정 여부와 마감일을 설정한다.
5. 스터디원이 배정 문제를 맞히면 `SubmissionJudged` 이벤트로 진행률이 자동 갱신된다. 기존 풀이·기한 내·지각 완료는 제출 접수 시각 기준으로 구분한다. 재채점으로 판정이 바뀌면 진행률이 다시 계산된다.
6. 마감 임박·목표 미달 시 알림을 받고, 문제집 종료 후 미해결 문제로 후속 문제집을 구성할 수 있다.
7. 스터디원은 게시판에서 소통하고, AC 풀이를 스터디에 공유해 Diff 비교·라인 댓글로 리뷰한다.

**모의 코딩테스트 흐름**

1. 스터디장·운영진이 공개 문제로 스터디 시험을 만들고 시작·종료 시각과 배점을 정한다. 생성 시 문제 수정 회차를 고정한다.
2. 현재 스터디원이 참가 등록한다. 시작 전에는 문제 목록·본문이 공개되지 않으며, 시작 전까지는 참가를 취소하고 다시 신청할 수 있다.
3. 시작 시각에 문제가 공개되고, 서버 시각 기준 잔여 시간이 표시된다. 참가자는 종료 전까지 여러 번 제출할 수 있고, 진행 중에는 공개 테스트 결과만 보이며 문제별 마지막 유효 제출이 점수가 된다.
4. 작성 중인 코드는 서버 Draft와 LocalStorage에 이중 저장된다. Draft는 `seq`가 큰 것만 반영된다.
5. 이탈 후 재진입하면 서버 Draft와 LocalStorage 중 `seq`가 큰 쪽으로 복구한다.
6. 시험 제출은 `contest-service`가 접수(시간·자격 검증, 접수 시각 기록)하고 Outbox 이벤트로 `judge-service`에 채점을 요청한다. 채점 파이프라인은 일반 제출과 같고, 시험 문맥이면 전체 테스트를 실행해 부분 점수를 계산한다.
7. 종료 시각에 마지막 제출 이후 변경된 Draft를 자동 제출하고, 이후 접수되는 저장·제출은 거절한다.
8. 종료 후 채점 진행률과 함께 잠정 순위를 시험 화면에 공개하고, 모든 제출이 `COMPLETED`되면 결과를 확정해 점수·순위를 공개하고 알림을 보낸다. `FAILED` 제출이 있으면 관리자 재처리 또는 사유를 남긴 0점 확정이 끝날 때까지 결과 확정을 보류한다.

**대회 흐름**

1. 관리자가 전체 공개 대회를 만들고 대회 전용 문제와 공개 시각을 설정한다.
2. 대회 시간 동안 제출하면 채점이 끝나는 대로 판정이 공개되고, ICPC 방식(맞힌 문제 수 → 패널티 시간, AC 전 오답 1회당 20분)으로 실시간 순위가 갱신된다.
3. 종료 후 모든 채점이 종결되면 DB 기준으로 순위를 재계산해 확정한다.

| 모니터링 | Micrometer, Prometheus, Grafana, CloudWatch | 큐 적체·채점 작업 적체·채점 지연·CPU |
| 인프라 | Docker, Docker Compose, AWS EC2·RDS·S3·SQS·SNS·IAM·Systems Manager, GitHub Actions(OIDC) | API는 arm64(t4g), 채점은 x86(c5)로 이미지 분기 빌드 |
| 프론트엔드 | Next.js·TypeScript·Tailwind CSS, Monaco Editor(편집·Diff), Netlify | AI 페어 프로그래밍 |

### 5.3 주요 설계 판단

| 판단 | 근거 | 감수한 단점 |
| --- | --- | --- |
| 도메인마다 서비스를 만들지 않고 Gateway + 7개 애플리케이션으로 묶는다. | 함께 변경되고 같은 데이터를 쓰는 기능(제출·채점, 시험·대회)을 한 서비스에 두어 서비스 간 호출과 분산 정합성 문제를 줄인다. 5명이 각자 1~2개 서비스를 소유할 수 있는 크기다. | 한 EC2에 JVM 8개가 떠 메모리 부담이 크다 → 서비스별 힙 상한을 두고 기준선 측정 후 사양을 확정한다. |
| 채점 엔진을 직접 만들지 않고 Judge0를 별도 서버로 운영한다. | 샌드박스(격리·자원 제한·언어 런타임)를 2개월 안에 안전하게 직접 구현하는 것은 보안 위험이 크다. 팀은 파이프라인·정합성·복구에 집중한다. | Judge0 호스트 요구사항(cgroup 등)과 운영 부담을 떠안는다. Judge0 장애가 곧 채점 전체 장애다. |
| 일반 풀이 채점 요청은 SQS가 아니라 DB 작업 테이블(`judge_jobs`)로 처리하고, 시험·대회 요청만 SQS로 받는다. | 일반 풀이는 `judge-service` 안에서 접수와 채점이 끝나 SQS 왕복이 완충 효과 없이 실패 지점만 늘린다. 재시도 간격·횟수·이력을 SQL로 조회·제어할 수 있어 운영 가시성이 좋다. 시험·대회는 소유 서비스가 달라 큐가 필요하다. | 큐가 주던 자동 완충이 없어 선점 동시성·백오프·서킷브레이커를 직접 관리해야 하고, 작업 테이블 폴링 부하가 RDS에 더해진다 → 3주차 기준선에서 폴링 활성/비활성을 비교 측정한다. |
| 도메인 이벤트는 SNS → 서비스별 SQS로 팬아웃한다. | `SubmissionJudged`는 5개 서비스가 각각 소비해야 하므로 SQS 단독으로는 팬아웃이 불가능하다. 관리형 서비스라 Kafka 운영 부담이 없다. | 순서 보장이 없고 최소 1회 전달이므로 모든 소비자가 멱등·순서 역전을 처리해야 한다. |
| 채점 결과 이벤트를 문맥별로 분리한다(`SubmissionJudged`/`ExamSubmissionJudged`/`ContestSubmissionJudged`). | 문맥마다 반영 정책과 필요한 필드가 달라, 한 이벤트에 `context` 필터를 거는 것보다 계약이 명확하다. | SNS 토픽·SQS 구독 설정이 문맥 수만큼 늘어난다. |
| 분산 트랜잭션(2PC·Saga 오케스트레이터) 대신 Transactional Outbox + 멱등 소비자로 최종 일관성을 맞춘다. | 채점 결과는 `judge-service`만 확정하고 다른 서비스는 "반영"만 한다. 보상 트랜잭션이 필요한 흐름이 거의 없다. | 반영 지연(수 초)이 생기고, Relay·정리 배치를 운영해야 한다. |
| 언어별 시간·메모리 보정을 두지 않고 공통 여유값으로 처리한다. | 기준 시간 제한을 C++ 정답 코드 최대 실행 시간의 3배 이상(최소 1,000ms)으로 잡아 언어 차이를 흡수한다. 언어별 배율은 문제마다 검증 비용이 크다. | 비효율 C++ 통과와 올바른 Python TLE가 함께 생길 수 있다 → 유의미한 차이가 확인되면 언어별 보정을 도입한다. |
| 문제 본문·이미지·테스트케이스를 크기와 무관하게 모두 S3에 저장한다. | 저장 위치가 하나여서 회차별 불변 경로와 접근 권한을 일관되게 관리할 수 있다. | 작은 데이터도 S3 왕복이 생기고, 본문에 연결되지 않은 이미지를 정리하는 배치가 필요하다. |
| 시험·대회 제출은 `contest-service`가 먼저 접수하고, Outbox 이벤트로 `judge-service`에 채점을 요청한다. | 마감 판정·참가 자격·자동 제출 중복 방지의 원천이 `contest-service`에 있다. 접수 시각을 시험 서비스가 기록하므로 `judge-service` 장애·지연이 마감 판정에 영향을 주지 않고, 동기 호출 없이 fail-closed 검증 문제를 없앤다. | 시험 제출은 `examSubmissionId`를 먼저 받고 채점 `submissionId`는 이벤트로 연결되어 추적 단계가 하나 늘어난다. |
| 자동 제출 중복 방지는 분산 락이 아니라 `(participant_id, problem_id, draft_seq)` 유일 제약으로 한다. | "같은 코드 버전은 한 번만 제출"이라는 요구를 DB 제약이 직접 표현한다. 락 TTL·Redis 장애 시 블로킹 위험이 없다. | 유일 제약 위반을 정상 흐름(이미 제출됨)으로 처리하는 코드가 필요하다. |
| 서비스 디스커버리(Eureka)·Config Server를 두지 않는다. | 인스턴스 수가 고정된 EC2 Docker Compose라 Compose 네트워크 DNS로 충분하다. 설정은 환경 변수·Parameter Store로 주입한다. | 동적 스케일아웃·무중단 설정 변경이 필요해지면 도입해야 한다. |
| DB는 환경별 RDS 1대에 서비스별 스키마·계정을 분리한다. | 비용상 서비스마다 RDS를 둘 수 없다. DB 계정 권한으로 소유권을 강제하고 교차 조인을 금지한다. | 물리적으로 한 인스턴스라 장애·부하가 공유된다. |
| 다른 서비스 데이터가 필요하면 동기 조회 대신 이벤트 복제본을 우선한다(예: 스터디원 목록, 회원 풀이 이력, 문제 난이도). | 소비 시점마다 동기 호출을 하면 장애가 전파된다. 채점 이벤트에 문제 난이도·태그 스냅샷을 담아 소비자가 추가 조회 없이 반영한다. | 복제본 지연·정합성 관리가 필요하다 → 이벤트 회차 비교와 내부 API 기반 재동기화 절차를 둔다. |
| 인증은 Gateway에서 JWT를 검증해 사용자 식별 헤더로 전달한다. | 서비스마다 토큰 검증 로직을 중복하지 않는다. | Gateway 우회 시 헤더 위조 위험 → 외부 식별 헤더 제거, 내부 포트 비공개로 방어한다. |
| 채점 결과·알림 전달은 WebSocket이 아니라 SSE를 쓴다. | 서버 → 클라이언트 단방향이면 충분하고, 3차에서 SSE 재연결 운영 경험이 있다. | 양방향 기능이 필요해지면 교체해야 한다. |
| 순위는 Redis Sorted Set으로 실시간 조회하고, 최종 순위는 DB에서 확정한다. | 조회는 빠르게, 최종 결과는 재계산 가능한 원천 데이터로 보장한다. | Redis와 DB 순위가 일시적으로 다를 수 있다 → 확정 시 DB 기준으로 Redis를 재구성한다. |
| 시험 제출도 일반 제출과 같은 채점 파이프라인을 쓰고, 문맥과 실행 옵션만 다르게 한다. | 채점 로직을 한 곳에만 두어 판정 불일치를 막는다. | 시험 마감 폭주가 일반 제출 대기에 영향을 준다 → 우선순위 큐 분리는 P3 후보 |
| 예약 작업은 Lambda·EventBridge가 아니라 각 서비스 내부 스케줄러 + ShedLock으로 처리한다. | 시험 종료·진단 만료·가입 만료 등은 해당 서비스 DB의 상태 전이라 소유 서비스 안에서 조건부 UPDATE로 처리하는 편이 단순하다. | 서비스가 중지되면 예약도 멈춘다 → 재기동 시 밀린 작업을 따라잡도록 "시각 도달 여부"로 판정한다. |
| 스터디 정원과 1인 참여 상한은 비관적 락이 아니라 카운터 컬럼의 조건부 UPDATE로 지킨다. 회원 카운터 → 스터디 정원 순서로 확보한다. | 검증과 증가가 한 문장에서 원자적으로 끝나 락 점유 시간이 가장 짧다. 정원은 스터디 기준, 상한은 회원 기준이라 락 대상이 달라 두 카운터가 모두 필요하다. 확보 순서를 고정해 교착을 막는다. | 카운터와 실제 가입 수가 어긋날 수 있다 → 가입·탈퇴와 같은 트랜잭션에서만 변경하고, 대사 쿼리로 검증한다. |
| 가입 시점의 문제집 편입은 이벤트가 아니라 가입 트랜잭션 안에서 처리하고, 개설 스케줄러와 같은 유일 제약 upsert로 합친다. | 같은 서비스 안의 상태 변화라 이벤트를 거칠 이유가 없다. 가입과 개설이 동시에 일어나도 두 경로가 모두 쓰고 유일 제약으로 합치므로 누락·중복이 없다. | 가입 트랜잭션이 진행 중 문제집 수 × 문제 수만큼 커진다 → 스터디당 동시 진행 문제집 수를 작게 유지해 영향이 작다. |
| 완료 유형은 제출 접수 시각과 문제집 기간만으로 계산하는 함수로 두고, 인정은 회차가 아니라 문제 기준으로 한다. | 이벤트가 개설 전후 어느 때 도착하든, 멤버가 언제 가입하든 결과가 같다(순서 비보장 메시징 대응). 서비스 전체의 "접수 시각 기준 마감 판정" 원칙과 일치한다. 일반 제출은 항상 최신 회차로만 가능하므로 회차 기준 인정은 완료 불가 상태를 만든다. | 채점 이벤트에 제출 접수 시각(`submittedAt`)이 필요하다 → 이벤트 계약의 필수 필드로 확정했다. |
| 태그 레벨·성취도는 저장값을 증감하지 않고 현재 데이터로 매번 재계산한다. | 이벤트 중복·순서 역전·재채점과 무관하게 같은 결과가 나온다. 재계산 범위가 태그 × 난이도로 작아 비용이 낮다. | 채점 결과마다 재계산이 일어나고, 재채점 결과로 레벨이 내려갈 수 있다 → 하향 사유를 알림으로 안내한다. |
| 힌트 차단 목록은 Redis가 아니라 `study` 스키마의 복제본 테이블에 두고, 차단 여부를 시험 시각으로 판정하며 요청·전달 시점에 두 번 확인한다. | 멱등 소비(`processed_events`)와 반영을 한 DB 트랜잭션으로 묶을 수 있다. Redis는 트랜잭션 밖이라 부분 실패 시 차단이 영구 누락되고, 데이터 유실 시 조용히 전부 허용된다. 시각 판정이라 시작 이벤트 지연의 영향이 없다. | 매 힌트 요청마다 DB 조회가 1회 늘어난다 → `(member_id, problem_id)` 인덱스로 처리하며, 힌트 요청량이 작아 부담이 작다. |
| 감사 로그는 별도 서비스로 모으지 않고 각 서비스가 자기 DB에 기록한다. | 감사 서비스를 분리하면 동기 의존이 생기거나 비동기 유실 위험이 있어 "누락 없음" 요구와 충돌한다. | 전체 감사 로그를 한 화면에서 조회하려면 여러 서비스 API를 조합해야 한다 → 필요해지면 분리를 검토한다. |
| AI 기능은 `study-service` 내부 모듈로 시작한다. | 초기에는 호출량이 작고 배포 주기가 같다. 인터페이스는 분리 가능한 형태로 만든다. | 분리 시점에 코드 이동 비용이 생긴다. |
| 관리자 기능은 데이터 소유 서비스의 `admin` 패키지에 둔다. | 관리자 서비스가 다른 서비스 DB를 직접 수정하는 구조를 막는다. | 관리자 화면이 여러 서비스 API를 조합해야 한다. |
| Spring Boot 4.1.1로 시작한다. | 3.5는 OSS 지원이 종료됐고 4.0도 2026-12에 끝난다. Spring AI 2.0 스타터가 Boot 4.1 기준이라서 AI 기능과 같은 버전 라인을 공유한다. | ShedLock 등 서드파티 라이브러리의 4.1 호환 버전을 직접 확인해야 한다 → 첫 주에 Gateway·서비스 1개·Spring AI를 포함한 골격으로 호환성을 확정한다. |

## 7. 검증 계획

| 영역 | 검증 내용 | 목표 |
| --- | --- | --- |
| 사용자 흐름 | 로그인 → 문제 풀이 → 스터디 진도, 시험 참가 → 저장·자동 제출 → 결과, 풀이 공유·알림을 Playwright로 검증 | 핵심 시나리오 통과 |
| 채점 정확성 | 문제별 정답·오답·TLE·MLE(테스트 환경 고려)·RE·CE 코드 세트로 판정 확인 | 판정 불일치 0건 |

### 8.3 주요 리스크

| 리스크 | 대응 |
| --- | --- |
| Judge0 호스트 요구사항(cgroup 버전 등)으로 최신 OS·EC2에서 정상 동작하지 않을 수 있다. | 1주차에 채점 EC2(c5.large)와 같은 AMI로 PoC를 먼저 수행하고, 실패 시 대체 엔진(Piston 등) 검토 결과를 2차 멘토링 전까지 확정한다. 로컬에서 격리가 안 되면 채점 어댑터 테스트(FakeJudgeClient)와 Linux 연동 검증을 분리한다. |
| 샌드박스 설정 실수로 AWS 자격 증명·내부망이 노출될 수 있다. | 채점 EC2에 IAM Role을 부여하지 않고, IMDS 차단·아웃바운드 제한·보안 그룹 최소 허용을 적용한다. 악성 코드 테스트 세트를 배포 검증에 포함한다. |
| API 서버(arm64)와 채점 서버(x86)로 아키텍처가 갈려 빌드·배포가 복잡해진다. | Docker 이미지를 플랫폼별로 빌드하고(`-platform linux/arm64`), 배포 문서에 플랫폼 분기를 기록한다. |
| API EC2 한 대에 JVM 8개 + Redis가 올라가 메모리가 부족하다. | 서비스별 힙 상한(-Xmx)·컨테이너 메모리 제한을 두고 3주차 기준선에서 메모리를 측정해 사양(t4g.large)과 비용을 재산정한다. |
| 채점 작업 테이블 폴링이 RDS 1대에 부하를 더한다. | 폴링 주기를 1초(빈 경우 최대 5초)로 두고, 3주차 기준선 측정에 폴링 활성/비활성 비교를 포함한다. |
| 채점 서버 CPU 부하 편차로 경계값 제출의 TLE 판정이 흔들릴 수 있다. | 채점 EC2는 고정 성능(c5.large)을 쓰고, `wall_time_limit`에 여유를 둔다. 경계값 TLE는 허용 리스크로 운영 문서에 기록한다. |
| 서비스 수가 늘어 로컬 실행·통합 디버깅 비용이 커진다. | Docker Compose 원클릭 실행, LocalStack, Correlation ID 로그, 서비스별 Mock 서버, 필요한 서비스만 띄우는 Compose 프로필로 완화한다. |
| 이벤트 중복·순서 역전으로 순위·진도가 틀어진다. | 멱등 소비 테이블과 회차 비교를 공통 라이브러리로 제공하고, 재전달 주입 테스트를 CI에 둔다. 레벨·성취도는 재계산 방식이라 순서와 무관하게 같은 결과를 낸다. |
| P1 범위가 커서 중간 발표 전 통합이 밀린다. | 3주차 말 P1 진척을 점검해 모의 코테·스터디 진도·Outbox 통합을 우선한다. 대회·추천 등 P2 기능은 P1 완료 후 착수한다. |
| LLM 비용·지연·장애 | 문제 단위 힌트 캐시, 1인 일일 제한, 타임아웃·서킷브레이커·정적 폴백 |
| 실운영 기간에 사용자가 오지 않는다. | 5주차에 부트캠프·기수·개발 커뮤니티에 모집 공지, 운영 기간 중 모의 코테·대회 이벤트로 방문 동기를 만든다. |
| 실운영 중 장애가 발표 일정 전체를 흔든다. | 운영 기간을 6주차로 고정하고 7주차는 개선·재측정에만 쓴다. 당번제와 장애 대응 절차를 미리 문서화한다. |
| 문제 저작권 | 타 사이트 문제를 복제하지 않고, 프로그래머스 고득점 Kit의 태그·난이도 구조만 참고해 팀이 자체 출제한다. |
| AWS 비용·비밀값 관리 | 예산 알림·운영 기간 외 중지 자동화, 비밀값은 GitHub Secrets·Parameter Store로만 관리한다. |
| 기능 범위 확대 | P0·P1 완료 전 P2 착수 금지, P3는 운영 결과를 본 뒤 선택한다. |
