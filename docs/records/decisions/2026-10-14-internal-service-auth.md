- 상태: 채택
- 결정일: 2026-10-14
- 확인: A(플랫폼·인프라), E(회원) 결정 / B·C·D는 확인
- 논의: [노션 서비스 간 인증 제안서](https://app.notion.com/p/3f7ac7091a7480d2af9ae970bd70a9d5)

## 결정

**제안 2(내부 네트워크 신뢰 기반 인증 생략)**를 채택한다.

- 내부 API(`/internal/v1/**`)는 서비스 토큰 인증 없이 호출한다.
- 외부의 `/internal/**` 요청은 Gateway가 403으로 차단하고, Nginx는 `/api/` 외의 요청을 백엔드로 전달하지 않는다. 백엔드 서비스 포트는 외부에 공개하지 않는다.
- 외부 사용자 인증(Gateway JWT 검증, `X-User-Id`·`X-User-Role` 전달)은 기존대로 유지한다.
- 사용자 데이터 검증은 이 결정과 별개로, 데이터를 소유한 수신 서비스가 수행한다(정책 및 상태 §1 검증 책임).

## 채택 근거

- 기존 구조와 기준이 일치한다. 각 서비스는 이미 Gateway가 전달한 `X-User-Id`를 신뢰하는 구조(내부망 신뢰 전제)이므로, 서비스 간 호출에도 같은 신뢰 경계를 적용한다. (E 확인)
- 추가 구현 비용이 거의 없다. 결정 시점에 외부 차단이 아래와 같이 구성되어 있다. (A 확인)

| 항목 | 결정 시점 상태 |
| --- | --- |
| Gateway 내부 경로 차단 | PR #39, `JwtAuthenticationFilter`에서 인증보다 먼저 `/internal/**`·`/**/internal/**`를 403으로 차단 |
| 외부 식별 헤더 제거 | PR #39, `RemoveExternalHeadersFilter` |
| 운영 인증 우회 차단 | PR #39, prod·staging에서 우회 설정 시 기동 실패 |
| Nginx 전달 범위 | prod는 `/api/`·`/gateway-health` 외 요청을 404로 응답 |
| Docker 포트 비공개 | Gateway·백엔드 서비스 포트 매핑 없음 |

## 기각한 대안: 제안 1 (member-service 서비스 토큰 발급)

- member-service·Redis가 내부 호출 전체의 장애 지점이 된다. 토큰 발급이 중단되면 5분 안에 모든 서비스 간 호출이 멈춘다.
- 서비스 토큰 발급·키 교체·허용 목록 관리를 직접 구현해야 해, 프로젝트 기간 대비 이득이 작다.
- 인스턴스 수가 고정된 Compose 구성(기획서 설계 판단)에서는 네트워크 경계로 충분하다.

## 재검토 조건

- 서비스가 여러 호스트로 분산되거나 신뢰할 수 없는 워크로드가 같은 네트워크에 들어오면 이 결정을 다시 검토한다. 
- 이때는 직접 구현하지 않고 Spring Authorization Server(client credentials)나 mTLS를 검토한다.
