## 결정

각 서비스의 `global` 패키지에 중복된 공통 기반을 라이브러리 모듈로 분리한다.

- **공통으로 관리할 대상**
  - 성공·오류·페이지 응답과 예외 기반
  - Gateway 사용자 식별·역할과 401·403 처리
  - 요청 추적 ID
  - 생성·수정 시각과 Clock·JPA 감사 설정
- **서비스에서 관리할 대상**
  - 서비스별 오류 코드·업무 권한
  - DB 제약 변환·도메인 상태
- **구현·적용 방식**
  - PR #64에서 `common-core`, `common-web`, `common-jpa` 세 모듈로 분리했다.
  - 사용할 설정은 서비스에서 명시적으로 등록한다.
  - 의존성 추가와 기존 코드 교체·연결은 별도로 진행한다.
  - 공통 코드 변경은 사용하는 서비스의 재빌드·재배포로 반영한다.

---

## 도입 배경

- **반복 수정:** 같은 공통 코드의 버그 수정·계약 변경을 서비스마다 적용해야 했다.
- **수정 누락:** 복사본별 수정 시점·내용에 따라 서비스의 처리 결과가 달라질 수 있었다.
- **당시 배포 방식:** 모노레포·단일 Docker Compose에서 전체 서비스를 재배포하는 방식을 전제로 논의했다.
  - 서비스별 복제본 유지보다 공통 수정의 일관성을 우선했다.

## 모듈 분리와 설정 등록

도입 범위와 결정일은 10월 15일 회의 기록을 기준으로 한다.
아래 모듈 분리와 설정 등록 방식은 이후 PR #64에 반영한 구현 설계다.

### 모듈 분리

| 모듈 | 분리 이유 |
| --- | --- |
| `common-core` | 응답·예외·시간 기준을 웹 보안·JPA 감사 구성과 분리한다. |
| `common-web` | MVC·Security·HTTP 요청 추적을 필요한 서비스에서 선택한다. |
| `common-jpa` | JPA 감사·시간 필드를 웹 구성과 독립적으로 선택한다. |

- `common-web`은 core 타입을 공개 의존성으로 제공한다.
- `common-jpa`를 사용해도 Entity·Repository 스캔과 DB 연결은 서비스가 담당한다.

### 명시적 설정 등록

- 공통 모듈은 Java 라이브러리로 제공한다.
  - 실행 애플리케이션이나 자동 설정 starter로 구성하지 않는다.
- 필요한 설정은 `@Import` 또는 컴포넌트 스캔으로 등록한다.
  - 의존성 추가만으로 예외 처리·인증 필터·JPA 감사를 모두 활성화하지 않는다.
  - 등록 대상을 서비스 코드에 드러내어 기존 설정의 교체·중복 여부를 확인한다.
- 경로별 권한과 보안 필터 체인은 서비스에서 구성한다.

| 방식 | 고려할 점 | 선택 |

| 서비스별 공통 코드 복제 유지 | 서비스별 변경·배포에는 유리 | 공통 수정의 반복·누락 방지를 우선 |

## 재검토 조건

- **독립 배포·저장소 분리 도입**
  - 공통 라이브러리 버전·배포 단위·호환성 관리 방식을 재검토한다.
- **서비스별 계약 차이 발생**
  - 공통 범위를 줄이거나 서비스별 구현으로 분리한다.
- **설정 등록 방식의 안정화**
  - 동일 등록이 반복되고 Bean 활성화·대체 조건이 안정되면 Auto-configuration을 검토한다.

서비스 적용 절차는 [공통 모듈 적용 가이드](../../guides/common-module.md)를 따른다.

내부 API의 신뢰 경계는 [서비스 간 인증 방식](2026-10-14-internal-service-auth.md)의 결정을 유지한다.
